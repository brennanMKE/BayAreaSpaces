# 0003 — Postgres publish target is undefined, blocking the handoff to the website project

## Description

The finished event set is meant to land in the existing Postgres database on AWS EC2, which the website project reads. Three questions are unanswered, and nothing can be written until they are — guessing here would bake a wrong assumption into the seam between two projects.

1. **Connection method** from the Mac mini: direct, SSH tunnel, VPN, or an API in front of the database.
2. **Schema ownership**: does this repo own the published table's shape, or does the website?
3. **Upsert semantics**: is the published set replaced wholesale each run, or merged on `uid`?

## Expected behavior

All three answered and recorded in `CLAUDE.md`, with `MAKER_CALENDAR_PG_DSN` (or whatever the connection turns out to need) documented in `.env.example`.

## Actual behavior

Recorded as open questions in `CLAUDE.md`. The pipeline emits to `out/` and treats that as the interface in the meantime, which is a fine interim state.

## Notes

Question 3 interacts with UID stability. If the table is replaced per run, a UID change is invisible to the database but very visible to subscribers. If it is merged on `uid`, a UID change silently duplicates every event. Either way the UID rules in `CLAUDE.md` are load-bearing.

This does not block Phase 1 (issues 0004–0012), which emits to `out/`.
