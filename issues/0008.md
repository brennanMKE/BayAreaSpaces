## Description

Thin wrapper over the `ics` adapter that builds the URL from a `calendar_id`. Covers Sequoia Fabrica's member/volunteer calendar and Maker Nexus's 11 MB class export.

## Expected behavior

- `https://calendar.google.com/calendar/ical/{quote(calendar_id)}/public/basic.ics`, then delegate to `ics`.
- URL-encode the `@` in the calendar id. One registered id uses `%40` and another a literal `@` — normalize both.
- Surface `X-WR-CALNAME`, `X-WR-CALDESC` and `LAST-MODIFIED` to the caller; the health gates need `LAST-MODIFIED` and the descriptions carry real information (Sequoia Fabrica's `X-WR-CALDESC` is what proved its calendar is disjoint from Bookwhen).

## Notes

Do **not** use `X-WR-CALNAME` as a source label — Humanmade's Luma calendar is named "Personal" and Maker Nexus's is "Amilia Published Classes".

Verify with a negative control: a bogus calendar id must 404. Maker Nexus's id was confirmed genuine that way, and the same technique proved Ace's category feeds actually filter.

Maker Nexus is 11 MB with history to 2023-12 — clip to horizon on parse, and let conditional GET do the heavy lifting.

## Root cause

Not a bug — a missing adapter. `sources.yaml` names `gcal_ics` for three sources (two enabled, one deliberately disabled) and `pipeline/adapters/` had no module for it, so those sources could be loaded and fetched but never parsed.

The one real hazard the work uncovered is the `@` in a Google calendar id. `fetch.resolve_url()` built the URL with `quote(calendar_id, safe="")`, which is correct for the literal-`@` spelling that `sources.yaml` uses but **double-encodes** the `%40` spelling that `references/feeds.json` and `spaces/sequoia-fabrica.md` / `spaces/maker-nexus.md` record for the same two calendars. `%2540group.calendar.google.com` is not a malformed request; it is a well-formed request for a calendar that does not exist, and Google answers it with a 404 HTML page. Copying an id out of a research note into the registry would therefore have dropped a whole space with nothing in the run erroring — the exact silent-empty-calendar failure CLAUDE.md is built around.

## Fix

`pipeline/adapters/gcal_ics.py`, a thin wrapper with a pure URL half and a fetch+parse half:

- `normalize_calendar_id()` decodes first (`unquote`), so `…%40group.calendar.google.com` and `…@group.calendar.google.com` collapse to one canonical id. `encode_calendar_id()` then encodes the decoded form with `safe=""`, which makes encoding **idempotent** and `%2540` unreachable. It raises `InvalidCalendarId` for an empty id, a `/`, whitespace, or a whole URL pasted into `calendar_id` — each of which would otherwise become a plausible-looking 404 rather than an error.
- `calendar_ics_url(calendar_id)` returns `https://calendar.google.com/calendar/ical/{encoded}/public/basic.ics`. Pure: no HTTP, no registry, no `FetchResult`, importable and testable on its own.
- `fetch.resolve_url()` now delegates to `calendar_ics_url()` (imported inside the function, since `gcal_ics` imports `fetch`). One implementation rather than two, so the pipeline and the adapter can never disagree about what was requested.
- `parse_gcal_ics(result, …)` delegates to `parse_ics`, which already returns post-expansion, horizon-clipped events and already surfaces `X-WR-CALNAME` / `X-WR-CALDESC` / `X-WR-TIMEZONE` and the newest `LAST-MODIFIED` (`IcsParse.last_change`, `IcsParse.stale_days` — issue 0016's `max_stale_days` input). No second parser and no second result shape.
- The wrapper adds exactly one judgement of its own: **a non-2xx from `calendar.google.com` is a reported failure** (`IcsProblem.NOT_CALENDAR`), never an empty calendar. Elsewhere in this registry a 404 can carry a good body, so the fetch layer refuses to pre-judge; Google is not that case, and a 404 there means a wrong, un-shared or double-encoded id.
- `fetch_gcal_ics(fetcher, ref, …)` goes through `Fetcher.fetch_url`, so the constructed URL still gets the same `robots.txt` decision, per-host rate limit and `raw/` archiving. `conditional=True` by default (`fetch_url`'s own default is off) because Maker Nexus is 11 MB; a 304 comes back as `NOT_MODIFIED`, which is "reuse the stored events", not zero.
- `X-WR-CALNAME` is surfaced and never used as a label; `IcsParse.label` stays the registry's, and a test asserts the two differ for Maker Nexus.

## Gotchas

- **Encode-after-decode, not encode.** `quote(unquote(id))` is what makes the two spellings converge and makes the operation idempotent. Plain `quote()` is right exactly once and wrong every time after.
- `%2540` fails as a 404, not as an error. Anything that builds this URL has to be the same code as everything else that builds it, which is why `fetch.resolve_url()` no longer has its own copy.
- All three ids in `sources.yaml` currently use the literal `@`; the `%40` spelling lives in `references/feeds.json` and the two `spaces/*.md` files. The registry is one copy-paste away from the encoded form at any time, so this is a live hazard, not a hypothetical.
- Google's 404 body is `text/html`, so `parse_ics` would already have reported it as `WRONG_CONTENT_TYPE`. The explicit status check exists to name the actual cause — wrong or un-shared calendar id — rather than making a human infer it from a content-type message.
- **`calendar.google.com/robots.txt` has not been read.** The fetch layer will consult it on the first live run and a disallow means we do not fetch, per CLAUDE.md. Check it when issue 0001 unblocks live requests; if it disallows `/calendar/ical/`, that is a question for the two spaces (who own the calendars), not something to route around.
- `noisebridge` / `noisebridge-today` stays `enabled: false`. A test asserts it is the only disabled `gcal_ics` source, so re-enabling it fails the suite loudly — it is the abandoned feed with five `UNTIL`-less RRULEs that invents ~5 events a week forever.
