## Description

RSS output via `feedgen`, so readers surface newly *announced* events rather than chronologically-next ones.

## Expected behavior

- **`pubDate` is when we first saw the event, not the event date.** This is the whole point — subscribers want to know what was just announced.
- Description carries the event date, space and price.
- One `<category>` per LLM-assigned tag (issue 0029); ship without categories until then.
- Link points at the space's own page.

## Notes

`first_seen` comes from SQLite (issue 0013) and must survive content edits, or every corrected typo re-notifies every subscriber.

Several sources carry an RSS feed whose `pubDate` is *not* the event date — that is a trap on the input side, documented per-source in the registry, and unrelated to what we emit. One exception worth knowing: Sudo Room's events RSS genuinely uses `pubDate` as the event start.

## Root cause

Not a defect — `pipeline/emit_rss.py` was a docstring-only stub scaffolded by issue 0004, and the run published `out/calendar.ics` and nothing else. The calendar answers "what is on next"; nothing answered "what was just announced", which is the question a reader is good at and a calendar client is not.

The thing that made this worth its own issue rather than fifty lines of `feedgen` is the `pubDate` decision. A feed dated by `start_utc` is the calendar with worse ergonomics, and a feed dated by "when this row was last written" re-notifies every subscriber the first time a space fixes a typo. Only `first_seen` is right, and only because issue 0013 already guarantees it is written once per `uid` and never updated.

## Fix

`pipeline/emit_rss.py`, built on the seams `emit_ics` already has rather than beside them.

- **`pubDate` is `first_seen`.** `first_seen_for(event, store)` prefers a live `Store.first_seen(uid)` lookup, falls back to `Event.first_seen` (which `record_events` has already reconciled to the stored value by the time the run loop hands the events over), and finally to the feed's build time for an event that has never been recorded. It refuses a naive datetime rather than guessing a zone, because a mis-zoned `pubDate` silently reorders the feed.
- **Newest first, capped at 200 by recency of first seen.** `sort_by_first_seen` orders newest-announced first with a UID tiebreak, so an unchanged event set renders byte-identical and a diff of two nights means something; `cap` slices the head. Capping by event date instead would evict exactly the far-future announcements the feed exists to carry.
- **Description carries date, price and space.** The body prefers `Event.summary_line` when `enrich` (0029) has written one, otherwise `emit_ics.truncate(description)` — the *same* function, not a second copy, so the two ~300-character cuts cannot drift apart. Then the event date in the space's own wall clock, `Price:` when known, and `{space name} — {link}` always.
- **Link matches `emit_ics`.** `event_link(..., prefer_event_url=True)` — the event's own page when the source gave one, the space page otherwise, never empty. `guid` is the UID verbatim with `isPermaLink="false"`.
- **One `<category>` per tag**, blanks and duplicates dropped; an event with no tags emits no element at all, which `validate_rss` asserts. `Event.categories` is the source's own list today and becomes the LLM taxonomy at 0029 with no change here.
- **Validate, then move into place.** `render` → `validate_rss` (round-trip through `ElementTree`: RSS 2.0 root, one channel with title/link/description, item count within tolerance, every item with title/link/description/`guid`/parseable aware `pubDate`, unique guids, newest-first ordering, no empty category) → `emit_ics.write_atomic`. A failure raises `InvalidFeedError` before anything moves, so the previously published feed survives.
- **Wired into the run.** `run_pipeline` calls `emit_rss` immediately after `emit_ics`, on the same event set, handing over the store. Both artifacts or neither — a feed that disagrees with the calendar is worse than no feed. `RunReport.rss` carries an `RssEmitResult` shaped like `EmitResult`, so `report.as_dict()["rss"]` lands in `health.json` for free, and `print_run_report` prints a `feed:` line. A dry run stages `calendar.ics` and `feed.xml` together under `out/.staging/` and touches nothing live.

## Gotchas

**`feedgen`'s `add_entry` prepends by default.** `add_entry(feedEntry=None, order='prepend')`. Sorting the events and then adding them in order produces a feed in exactly reverse order, which for this feed means oldest-announced at the top — the one arrangement that makes it useless. `order="append"` throughout, and `validate_rss` asserts newest-first on the parsed output rather than trusting the builder.

**`feedgen`'s channel `<link>` is the *last* link registered, not the first.** Its own source comment says "We use the first link for RSS" directly above `self.__rss_link = self.__atom_link[-1]['href']`. Registering `rel="self"` before `rel="alternate"` is what keeps the human-facing page in `<link>` while the `atom:link rel="self"` still appears. There is a test pinning this, because the bug is upstream and silent.

**`Event.categories` is the source's categories, not the LLM's.** The issue text says "ship without categories until 0029"; the code instead emits whatever is on the record, which today is the source's own list and after 0029 is the taxonomy. Nothing in `emit_rss` changes when that swap happens. The case that needed care is the empty one — most sources supply nothing — and an empty `<category></category>` renders as a blank tag chip forever in readers that show categories.

**`first_seen` has three sources and they must be tried in that order.** The store row is the authority. The record is the fallback and is normally the same number. The build time is the last resort, and it is the *correct* answer for `--dry-run`: a dry run records nothing, so every item is "announced tonight" — right for a staged artifact nobody is subscribed to, and wrong-looking until you notice the staging directory.

**The cap is on announcement age, not event date.** Stated twice in the module and tested with the two orders deliberately inverted, because "keep the newest 200" reads as if it could mean either and one of the meanings drops the announcements.
