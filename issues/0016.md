## Description

The failure that actually bites is not a crash — it is a source quietly going wrong while the run succeeds. Gates run **before** anything is published.

## Expected behavior

Baseline gates:

- Per source: 0 events when the previous run had >0 → do not publish, carry forward, alert.
- Global: total dropped more than 40% night over night → do not publish, alert.
- `start_utc` more than 2 years out, or in the past → drop and log.
- Empty title, or title over 200 chars → quarantine.

**Per-source overrides, each required by a real source in the registry:**

| Override | Why it exists |
|---|---|
| `max_stale_days` | Noisebridge's retired gCal: 28 VEVENTs, dead since Jan 2024, five RRULEs with no `UNTIL`. Invents ~5 events a week **forever, at a constant rate**, and passes every count-based check. Gate on `LAST-MODIFIED` age. |
| `allow_zero` | The Box Shop (~8–12 events/year) and Lower 48 are routinely empty. Without this they alert monthly and you learn to ignore alerts. |
| `ignore_count_drop` | Hacker Dojo's Meetup iCal caps at 10 with no pagination — a ~1-week horizon, so nightly deltas are noise. |
| `require_nonzero_once` | Humanmade's Eventbrite has never been non-zero, so "went to zero" can never fire, but a naive alert fires nightly. |

**Two counting rules:**

- Count **post-expansion events inside the horizon**, never raw records. 89 vs ~7, 3645 vs 171, 5057 vs 73.
- A short publishing horizon is not a decline. Maker Nexus posts 4–8 weeks ahead (Aug 112, Sep 43, Oct 16), so the far end of a 120-day window is legitimately empty every night.

## Notes

The `max_stale_days` case is the important one and the least obvious: our original gate design would have published fabricated events indefinitely while reporting perfect health.

## Root cause

Not a bug — a missing stage. Issue 0012 left a seam (`evaluate_health`, returning `implemented: false`) so the exit-code contract would be real code rather than a comment, and `pipeline/health.py` was a docstring with no gates behind it. Every run therefore published whatever the pipeline produced, which is fine while every source is healthy and catastrophic the first night one is not.

The deeper cause is that counting is the obvious gate and it is not sufficient. Four sources in this registry each break a count-based gate in a different direction, and the worst of them — Noisebridge's retired gCal, 28 VEVENTs with five `UNTIL`-less RRULEs, dead since January 2024 — breaks it by looking *perfect*: it emits the same number of plausible events every night forever. Counting alone would have published invented events indefinitely while reporting full health.

## Fix

`pipeline/health.py` now runs before the emit step and can refuse.

**The gate metric is `horizon_count`** — post-expansion events inside the horizon — everywhere. Nothing in the module reads `raw_count`, because in this registry raw counts answer a different question (89 VEVENTs for ~7 live events, 3645 for 171, 5057 for 73). The night-over-night baseline is also a `horizon_count`, read from `run_source` via `Store.source_history`.

**Blocking conditions**, and deliberately only these:

- Per source: `horizon_count == 0` when the previous run had more than zero.
- Per source: `stale_days > max_stale_days`.
- Global: total dropped more than 40% night over night. "More than" is strict — exactly 40% publishes.

**Non-blocking conditions**, reported and where appropriate alerted: a per-source count drop over 50%, a feed that dates nothing at all while `max_stale_days` is configured, filters removing everything a source produced, a first night at zero, a source still at zero.

A per-source drop is alert-only *by design*. Maker Nexus posts 4–8 weeks ahead (Aug 112, Sep 43, Oct 16), so the far end of a 120-day window is legitimately empty every night; blocking the whole calendar because one space's publishing horizon breathes would train everyone to ignore the gate, which is the same failure as alerting monthly on The Box Shop.

**The four overrides**, merged space-level into source-level (booleans OR, the tighter `max_stale_days` wins) so The Box Shop and Lower 48 can declare `allow_zero` once for every feed they own:

| Override | Source | Behavior |
|---|---|---|
| `max_stale_days` | Noisebridge's retired gCal (180) | Blocks on `LAST-MODIFIED` age regardless of how healthy the count looks. |
| `allow_zero` | The Box Shop, Lower 48 | Zero is never a reason to block or alert. |
| `ignore_count_drop` | Hacker Dojo's Meetup iCal | Suppresses the drop alert; **still catches zero**, per the registry note "only alert on 0 after a run with >0". |
| `require_nonzero_once` | Humanmade's Eventbrite, Hacker Dojo's Luma | Quiet while `Store.has_ever_returned_events` is false; gates normally the moment it becomes true. |

**Layering for the two event-level rules.** The sanity window (`start_utc` in the past or beyond `MAX_FUTURE_DAYS`) and the title rules (empty, or over `MAX_TITLE_CHARS`) already exist in `normalize.py` from issue 0009, and the gate does not re-drop what normalize dropped. normalize owns them at **source scope** — it sees the raw event and its counts land on that source's record. health owns them at **publish scope**: `audit_events` re-applies the same two rules, importing the same two constants so the layers cannot drift, to the set that is actually about to be written — after carry-forward replay, after dedupe. In a healthy run it removes nothing, so `record.dropped_count` (normalize's) and `verdict.dropped_count` (the gate's) never count the same event. A non-zero gate count means something reached publication without passing through normalize. The action is "drop and log" / "quarantine" exactly as specified: the events are removed from the publish set and logged, and this does not block the run.

**Interactions.** A 304 (`reused_unchanged`, issue 0014) is exempt from both the zero gate and staleness — nothing changing is the definition of a 304, and `apply_carry_forward` has already restored its `horizon_count` to the replayed set, so it can never read as a zero.

**Documented policy — carried-forward sources.** A carried-forward source is recorded `degraded` and does **not** block. It is already degraded, already visible in `health.json`, already alerted by carry-forward, and already on the three-night escalation clock. Blocking would take the other ten spaces off the calendar to punish one transient 503 — the exact inversion of the invariant that a failed source must never silently delete a space. When escalation stops the replay on night three the events genuinely disappear, and at that point the **global** gate is free to notice, which is the right level for "we lost a material fraction of the calendar".

**Documented policy — blocked sources.** A `blocked` source (robots.txt) is `exempt`: it never blocks and never alerts. The disallow was honored, which is the correct outcome, not a failure of ours; letting one host's preference become our nightly outage would be absurd, and an alert that fires every night for a state nobody intends to change is the noise that buries real alerts. It stays present as a source verdict so issue 0017 can render it.

**The verdict object** (issue 0017 reports it, 0032 alerts on it):

```
HealthVerdict
  blocked: bool                      blocks_publication is the CLI's question
  reasons: tuple[str, ...]           BLOCKING messages only; what the store keeps
  notes: tuple[str, ...]             non-blocking observations
  alerts: tuple[str, ...]            everything 0032 should tell a human
  global_reasons: tuple[GateReason]  code + message + blocking + alert
  sources: tuple[SourceVerdict, ...]
  event_count / previous_event_count / drop_fraction
  dropped_count / quarantined_count / audit
  run_id / previous_run_id / space_filter / checked_at
  thresholds / gate_issue / implemented
  events                             the audited publish set; NOT in as_dict()

SourceVerdict
  space_id / label / key / status
  outcome: ok | exempt | degraded | blocked | not_evaluated
  blocked / reasons / codes / messages / blocking_reasons / alerts / overrides
  horizon_count / event_count / previous_count / delta / drop_fraction
  stale_days / max_stale_days / ever_nonzero
  carried_forward / reused_unchanged / escalated
```

Stable reason codes, for 0032 to key an alert policy on rather than parsing prose: `zero_after_nonzero`, `zero_no_baseline`, `zero_again`, `stale_feed`, `no_last_modified`, `count_drop`, `filtered_to_zero`, `allow_zero`, `ignore_count_drop`, `require_nonzero_once`, `reused_unchanged`, `carried_forward`, `escalated`, `blocked_by_robots`, `not_in_run_set`, `global_count_drop`, `global_ok`, `global_no_baseline`, `global_gate_skipped`.

**CLI wiring.** `run_pipeline` calls the gate after dedupe and before emit, replaces the event list with the audited one, writes each source's verdict onto its `run_source` row via `Store.set_gate_outcome`, and on a block sets `EXIT_HEALTH_BLOCKED` (1), writes nothing, and closes the run row with the blocking reasons. `HealthDecision` remains as an alias of `HealthVerdict` so issue 0012's contract keeps its name.

## Gotchas

- **The run row for tonight already exists when the gates run.** `run_pipeline` calls `record_source_run` inside the fetch loop, so `source_history` returns tonight's row first. Every history lookup filters on `run_id`; forgetting that would compare tonight against itself and no gate would ever fire.
- **The night-over-night baseline is the last night the source *answered*, not literally the previous run.** A source that fails records a zero it never produced. Taking that literally would mean a feed that fails once and then serves an empty document forever compares zero against zero and never trips again. `previous_source_count` skips `failed`/`error` rows within a 14-run window; the failure itself is not lost, because carry-forward reports and escalates it.
- **`--space` runs are excluded from the global gate in both directions.** Their event set is one space's worth by construction, so comparing one against a full run reports a collapse that did not happen — and `previous_total` skips filtered and dry runs so a `--space` run cannot poison tomorrow's baseline either.
- **`ignore_count_drop` does not mean "ignore zero".** Easy to write, wrong: the registry note on Hacker Dojo's Meetup feed is explicit that zero after non-zero is still the one thing worth alerting on. There is a test for exactly this.
- **`require_nonzero_once` reads `source_milestone`, which is written on `event_count > 0`, not `horizon_count > 0`.** A source whose filters remove everything it produced would not set the milestone. That is the conservative direction (it stays exempt longer), but it is a real asymmetry with the gate metric and worth knowing about.
- **Gate on `horizon_count`, report `event_count`.** A source can have a healthy `horizon_count` and publish nothing because its filters matched nothing — Humanmade's `title_contains: ["@ Humanmade"]` is indistinguishable from a broken filter from inside the gate. It is reported as `filtered_to_zero` and never blocks, because a working filter must not be able to stop the calendar.
- **A 304 with nothing stored is not exempt.** `reused_unchanged` is only true when events were actually replayed; a 304 whose stored set is empty falls through to the ordinary zero gate, which is right — we have no data for that source either way.
- **`evaluate_health` takes everything but `records` as keyword arguments with defaults**, so it stays callable from a test with nothing but a list. Without a store the night-over-night gates report "no baseline" rather than silently passing, which is the distinction issue 0012 drew between a declared absence and a lie.
