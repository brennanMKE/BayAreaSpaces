## Description

Parse RSS/Atom. The critical constraint: **most RSS feeds are not event sources**, because their `pubDate` is when the post was published, not when the event happens.

## Expected behavior

- Parse RSS 2.0 and Atom.
- **Require an explicit per-source declaration of whether `pubDate` is the event start.** Do not guess. Default to treating the feed as change-detection only.
- When a feed is change-detection only, emit no events — surface a liveness signal for `health.json` instead.
- Support two-step use: enumerate item `<link>` URLs as a seed list for another adapter (The Box Shop, The Crucible).

## Notes

Per-source truth established 2026-08-05:

| Feed | `pubDate` means | Usable as events? |
|---|---|---|
| Sudo Room `/events/feed/` | **event start** | Yes — the one genuine case |
| Meetup `/events/rss/` (all spaces) | post date | No — enumerated every tag to confirm |
| The Box Shop `/events?format=rss` | post date | Seed list only |
| The Crucible `/category/upcoming-events/feed/` | post date | Seed list only; dates live in title text like `(JUL 16)` |
| Mastodon `.rss` | post date | Announcement signal only |

Mastodon and Bluesky feeds are registered at `trust: 10` as change signals. Both of Sequoia Fabrica's are stale (last posts 2025-12-23 and 2025-07-08); Instagram is their live channel and has no feed.

**Two traps:** Ace's `/calendar/feed/` returns **404 with a populated 9.8 KB RSS body** — a body-trusting parser ingests it, a status-checking parser drops it. The Crucible returns **404 with `Content-Type: application/rss+xml` over a 1.35 MB HTML body** — there the header lies. Check status, content type and parse result, and treat disagreement as failure.

## Root cause

Nothing was broken; `rss` was the ninth of the ten registry adapter names and had no implementation, so its three registered sources skipped nightly with "adapter 'rss' is not yet implemented".

The real problem the adapter had to solve is that **an RSS feed does not say what its dates mean.** `<pubDate>` is a date in a plausible place, and whether it is the announcement or the event is a per-source fact that only a human who fetched the feed knows. Reading it wrong does not error: it publishes a full calendar of announcement dates, every entry plausible, nothing downstream ever objecting. Of the five feed families surveyed on 2026-08-05, exactly one (Sudo Room's `/events/feed/`) carries event starts.

The two 404 traps are the same problem one layer down. A parser that trusts the body ingests Ace's non-existent endpoint; one that trusts the status is still fooled by The Crucible's `application/rss+xml` header over an HTML error page. Each single fact is defeatable on its own.

## Fix

`pipeline/adapters/rss.py` (new), with the 2026-08-05 per-source table in the module docstring.

**The declaration is registry configuration, required at load time.** `Source.pubdate_means` (`event_start` | `post_date`) is mandatory for `adapter: rss` and forbidden elsewhere; `Source.rss_mode` (`events` | `change_detection` | `seed_list`) is optional and defaults to `change_detection`. Both are validated against `pipeline.adapters.rss.PUBDATE_MEANINGS` / `RSS_MODES` by a lazy import inside `Source._check_target`, exactly as `shape` is validated against `json_doc.SHAPES` (issue 0022). `rss_mode: events` over a `post_date` feed — the one pairing that would lie — is rejected by the loader. Called with no declaration at all (a test, or a file out of `raw/`), the adapter takes the change-detection default and sets `RssParse.declared = False`; the fallback publishes nothing, because the safe default for a feed nobody has classified is not a calendar.

**Three outcomes that all report zero events, and none of them look alike:**

| Outcome | `ok` | Signature |
|---|---|---|
| Change signal | true | `reported_change_signal`, populated `RssLiveness` |
| Seed list | true | `seed_urls`, `skipped_seeds` with reasons |
| Parsed and found nothing | **false** | `RssProblem.NO_ITEMS`, `liveness is None` |

`RssLiveness` carries the item count, newest and oldest item dates, the channel `lastBuildDate`, the newest title, and a `sha1` digest over the items' own identities — a change detector that needs no dates, for the feed that stops dating its posts. `age_days` is `None` unless the dates are declared post dates. It reaches `health.json` through fields the CLI already records (`raw_count`, `last_change`, `stale_days`) plus `RssParse.as_signal()`.

**Staleness only from dates that mean freshness.** `last_change` uses the channel's `lastBuildDate` always, and item dates only for a declared `post_date` feed. Sudo Room's newest item is 2027-01-01; calling that "fresh" would be the same error as publishing an announcement date as a start.

**Seed lists are reported, never followed.** `item_links()` applies the same rule as `jsonld.seed_links` (namespace-agnostic, `rel="alternate"` only), off-host links and robots-disallowed `?format=` routes are dropped with a reason, and `jsonld` does the actual fetching through its existing `paginates` seam so the follow-ups stay inside one rate limiter and one `raw/` archive. A test pins the two implementations together on `jsonld`'s own fixture.

**The 404 policy, applied to both traps.** The body is parsed first, always, even under a 404, so the report can name what was there. Then: a non-2xx status is fatal whatever the body turned out to be (`HTTP_ERROR`) — Ace's endpoint is one the server says does not exist, its canonical events RSS is a different URL, and failing lets issue 0014 carry yesterday's events forward; a body that is not a feed is fatal even at HTTP 200 under an `application/rss+xml` header (`NOT_FEED`), because `body_shape()` reads bytes and the header gets no vote; and a real feed under a type that is neither XML nor lenient is `WRONG_CONTENT_TYPE` rather than being waved through. Every contradiction found is kept verbatim in `RssParse.disagreements`, including tolerated ones (`text/plain` over a real feed).

Registered in the CLI dispatch table with `needs_source=True` (the declaration comes from the registry) and `paginates=False` (one request, ever). `sudo-room/mastodon` gained `health: allow_zero` — it contributes zero events by design, so a zero gate can never mean anything there.

## Gotchas

- **A `-0000` pubDate is naive on purpose.** RFC 5322 says it means "local time unknown", and `email.utils.parsedate_to_datetime` returns a naive datetime for it. It is passed on naive with `dtstart_form="floating"` so `normalize.py`'s floating policy — which logs, counts and reports — decides, rather than the adapter silently stamping Pacific on it. That is one `TimezoneConversion` per such item in the run report, and it is meant to be visible.
- **A feed can mix aware and naive dates in one document**, and comparing them raises. `_liveness` and `_staleness` both consider aware values only; the naive ones still become events.
- **The route order in `tests/test_cli.py::calendar_transport` matters.** `sudoroom.org/events/feed/` starts with `/events/`, which is the JSON-LD route's prefix. The RSS route has to come first or the run's counts start measuring an adapter correctly rejecting a payload it was never pointed at.
- **`allow_zero` on a change-detection source is not optional bookkeeping.** Without it the zero gate emits a note every night for a source that is doing exactly what it is registered to do, and nightly noise is how alerts get ignored.
- **`rss_mode: events` needs `pubdate_means: event_start`, and the loader enforces it** — but `_declaration()` also downgrades the pairing to change detection if it ever arrives anyway. Two guards, neither trusting the other, same shape as `orderby=date` / `min_total` in issue 0022.
- **Ace's `/calendar/feed/` is deliberately not in `sources.yaml`.** The trap fixture exists so the policy is tested; registering the URL would be trusting a 404. Its canonical events RSS is `?post_type=tribe_events&feed=rss2`, and Ace already has three better sources.
- **The Crucible's seed source stays `enabled: false`.** The adapter can produce its link list today, but the consumer for those `/event/<slug>/` pages is `llm_html` (issue 0028), which does not exist yet.
