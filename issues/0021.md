## Description

New adapter: parse a **named** `<script type="application/json" id="…">` blob out of a server-rendered page and map its bespoke shape. Not covered by anything existing — `jsonld` is schema.org-specific, `nextdata` is hardcoded to `__NEXT_DATA__`, and `json` expects a standalone document at a URL.

Consumer: The Crucible, the largest clean catalog in the registry.

## Expected behavior

- Configurable `script_id` (The Crucible uses `ac-course-data`) plus a field map.
- Decode `start_dates[]` as **Unix epoch seconds, local America/Los_Angeles**. Verified against the product page's `Class.Date` attribute to the minute.
- UID `{id}:{start_epoch}`.
- Skip the 9 courses with an empty `start_dates` array.
- **Each `start_date` is one RUN of a course, not one meeting.** A 5-week 20-hour course is one entry — which is what a merged calendar wants.
- **Do not compute `DTEND` from `hours`** — that field is total course hours, not session length, so it would render 40-hour blocks.
- Unescape HTML entities before matching filters: the blob stores `Glass Fusing &amp; Slumping`.

## Notes

Verified 2026-08-05: 132 KB blob, 216 courses, 478 offerings, **271 inside 120 days**. Cross-validates against the WooCommerce API's 274 (issue 0022).

There is **no XHR endpoint and no server-side filtering** — `?department=` and a bogus `?department=ZZZ` return the identical 216-course blob. All filtering in their UI is client-side.

`/shop/` carries a byte-identical blob; do not ingest both.

`nextdata` could later be reimplemented on top of this adapter — it is this with `script_id` fixed.

## Root cause

Not a defect — a missing adapter. The Crucible is the largest clean catalog in the registry and every existing adapter is wrong for it in a way that fails *silently*:

- `jsonld` finds `application/ld+json` and `@type: Event`. The Crucible's pages carry `schema.org/Course` with no `startDate`, no `offers` and no `hasCourseInstance`, so a `jsonld` source there returns empty forever without ever erroring.
- `nextdata` is hardcoded to `__NEXT_DATA__` and Eventbrite's `props.pageProps.upcomingEvents`; `thecrucible.org` is WordPress/PHP and has no `__NEXT_DATA__` anywhere.
- `json` expects a standalone JSON document at a URL, not a blob embedded in a 1.8 MB HTML page.
- `tribe_rest` is the trap: the pages are full of `tribe-*` CSS class names (inert Avada compatibility styles) while every `wp-json/tribe/*` route 404s.

The catalog is a **named** `<script type="application/json" id="ac-course-data">` blob, filtered entirely in client-side JavaScript. Nothing existing reads that.

## Fix

`pipeline/adapters/embedded_json.py`, following the `jsonld`/`tribe_rest` conventions: a frozen `EmbeddedJsonEvent(IcsEvent)`, an `EmbeddedJsonParse(IcsParse)`, a problem enum, and no exception ever raised for a bad payload.

- **Configurable `script_id`** plus a `FieldMap` whose every value is a **dotted path** (`resolve_path` walks nested objects *and* list indices). `CRUCIBLE_FIELD_MAP` is the default. `FieldMap.items` addresses the item list, so `script_id="__NEXT_DATA__"` with `items="props.pageProps.upcomingEvents"` is a working configuration — this is the generalization the research file asked for.
- **`start_dates[]` are Unix epoch SECONDS, local `America/Los_Angeles`.** An epoch is an instant, so nothing is guessed; `parse_epoch` converts in the zone and the event still carries `tz = "America/Los_Angeles"` — a **resolvable IANA name**, because `normalize.day_start_utc` and issue 0016's health filter call `ZoneInfo` on it and that filter runs outside the per-source `try`/`except`.
- **UID `{id}:{start_epoch}`**, which `normalize.py` namespaces to `{space_id}:{id}:{start_epoch}`. `recurring=False`: these are independent runs, not RRULE occurrences, and the epoch is already in the UID.
- **One event per `start_date`, i.e. one per RUN of a course**, never one per meeting.
- **`end=None`, always.** `hours` is carried on the event for diagnostics and is never used for `DTEND`. Deriving an end for apparently-single-meeting courses (`hours <= 8`) was considered and declined: the blob carries no per-meeting data at all, so that test is an inference about a field nobody measured.
- **Empty `start_dates` are skipped and counted** (`undated_item_count`, `undated_ids`); the epoch-`0` sentinel is dropped explicitly and counted separately (`bad_date_count`).
- **`html.unescape` on every text field**, so the emitted title is `Glass Fusing & Slumping` while the blob still says `&amp;`.
- **`location=None`** — the catalog has no location field of any kind, so `VenuePolicy` applies the space's mandatory `address_override`.
- **Five distinct failure modes**, because they have five different fixes: `NO_SCRIPT_ID` (nothing configured), `SCRIPT_NOT_FOUND` (drifted; the error names the JSON blob ids that *are* present), `NOT_JSON`, `NO_ITEMS` (shape changed under the same id), `NO_DATES`.
- **`blob_digest`** (`sha1[:16]`) is published so `/shop/`'s byte-identical mirror can be confirmed in one line rather than registered as a second source.
- `pipeline/cli.py`: `AdapterEntry` gains **`needs_source`**, a seam beside `paginates`. `embedded_json` needs the `SourceRef` (for `script_id`) and makes no further requests, so it gets the ref and not the `Fetcher` — "wants configuration" and "will make more HTTP requests" are different promises.

`sources.yaml` needed no change: `script_id` and the space entry were already there, and `config.py` already refuses an `embedded_json` source without a `script_id`.

## Gotchas

- **`tz` must be an IANA name even though the epoch is unambiguous.** The instant needs no zone; everything downstream does. `ZoneInfo("UTC-07:00")` is an error, and issue 0016's health filter runs outside the per-source `try`/`except`, so getting this wrong takes down the whole run rather than one source. Same finding as issue 0020.
- **Script bodies are raw text in HTML.** libxml2 does not decode entities inside `<script>`, so `&amp;` survives into the JSON string and unescaping is the adapter's job. A test asserts the raw blob still contains `&amp;`, so the day a parser starts decoding it, we find out.
- **`hours` looks exactly like a duration and is not.** It is the whole course. This is the single easiest way to wreck this source, and it fails *plausibly* — a 40-hour block renders, it just renders wrong.
- **The empty-`start_dates` courses have to be counted, not merely skipped.** Nine silently absent courses look identical to nine courses that were never there.
- **Do not add `?department=` to the fetch.** Verified: the parameter, a bogus value and `?ac_department=` all return the identical 216-course blob, and there is no XHR endpoint at all. A comment lives in `fetch_embedded_json` where someone would otherwise try.
- **`/shop/` is a byte-identical mirror.** Registering both would double every event and then hand the mess to dedupe. `blob_digest` exists so that can be checked without registering it.
- **`stocks[]` is deliberately unused.** It happened to be the same length as `start_dates` on the one sampled course. That is a suggestion of index alignment, not knowledge of it, and publishing seats against the wrong date would be wrong data that looks right.
- **The registry's `script_id` reaches the adapter through a new seam.** Reusing `paginates` would have handed it a `Fetcher` it has no use for and implied requests it never makes; `needs_source` says what is actually true.
- **`nextdata` (issue 0023) should be built on this.** `resolve_path`, `FieldMap.items` and `start_format` were written for it, and a test drives a `props.pageProps.upcomingEvents` payload through them. What that issue still owes is Eventbrite-specific: `start_date` + `start_time` + `timezone` as three fields, and `primary_venue.address`.
