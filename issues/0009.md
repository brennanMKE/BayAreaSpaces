## Description

The stage where the two invariants that quietly destroy the project get enforced.

## Expected behavior

**Timezones.** Parse to an aware datetime immediately, store UTC, carry the original tz string. **Assert and fail the run if a naive datetime reaches this module** — this is a hard failure, not a warning. Python does not enforce it structurally the way Go's `time.Time` would, so the assertion is the enforcement.

**UIDs.** If UIDs churn, every subscriber sees every event as new every night.

- Source supplies a UID (all ICS feeds do): keep it, namespaced `{space_id}:{source_uid}`.
- Otherwise `sha1(space_id + start_utc + normalize(title))[:16]`, where `normalize` lowercases, strips punctuation and collapses whitespace.
- **Never** include a scrape timestamp, page position, or any LLM output in a UID.

**Per-source UID rules already established:** Maker Nexus's JSON cache is keyed `YYYY-MM-DD_<amiliaId>` — use the key. The Crucible's blob gives `{id}:{start_epoch}`. Meetup iCal supplies stable `event_<id>@meetup.com`.

**Address overrides.** Apply `address_override` where set — Sudo Room ships the pre-2014 `549 48th St` on every event, Hacker Dojo's Meetup feed has no `LOCATION` at all, and The Crucible's catalog has no location field of any kind. Sudo Room's Luma feed carries genuinely off-site events, so check `LOCATION` before overriding it.

## Notes

Also enforce: drop events starting more than 2 years out or in the past, and quarantine empty titles or titles over 200 characters (a classic LLM-extraction signature).

## Root cause

Not a bug — the stage had never been written; `pipeline/normalize.py` was a docstring left by issue 0004's scaffold. But two things in it were genuinely wrong before a line was written.

**The documented UID rule was incorrect.** `{space_id}:{source_uid}` is only unique before RRULE expansion. Every occurrence of a series carries the same `UID`, so namespacing on the two-part form alone collapses a whole series into one event. One Sudo Room series has 17 occurrences sharing a single UID. The failure has no error mode: the feed keeps working and simply carries suspiciously few events, which is the worst-shaped failure this project has. `RECURRENCE-ID` cannot be used to detect the case either — `recurring-ical-events` sets it on *every* expanded occurrence, including non-recurring ones. CLAUDE.md was corrected in the same pass and this issue implements the corrected rule.

**Python cannot enforce the timezone invariant structurally.** Go's `time.Time` always carries a location; a Python `datetime` does not, and arithmetic on a naive one silently produces an answer that is wrong by 7 or 8 hours depending on the month. CLAUDE.md's language decision records this explicitly and defers the enforcement to an assertion in this module, so this module *is* the enforcement.

## Fix

`pipeline/normalize.py`, source-agnostic by construction: adapters hand it a `RawEvent`, and `from_ics_event` / `normalize_ics` are the ICS-shaped front door rather than the interface.

**Timezones.** `to_utc()` raises `NaiveDatetimeError` on a naive value unless the caller states a zone explicitly in code — there is deliberately no default. It raises rather than asserting, because `python -O` strips `assert` and an invariant that an interpreter flag can switch off is not an invariant. `Event.__post_init__` re-checks `start_utc`, `end_utc`, `first_seen` and `last_seen` on every instance, so a naive value cannot reach the canonical record by any path.

**Floating-time policy (documented, and the reason the assertion still fires usefully).** Issue 0007 passes floating times — no `TZID`, no `X-WR-TIMEZONE` — through naive on purpose so they arrive here. A floating time is *interpreted*, never rejected: the zone comes from the calendar's `X-WR-TIMEZONE`, else the space's registry timezone, else `defaults.timezone` (`America/Los_Angeles`). Every conversion is logged at `WARNING`, recorded on the result as a `TimezoneConversion`, and stamped `tz_assumed=True` on the event. The strictness lives in what does *not* qualify: a naive datetime arriving while the adapter **declares** a zone (`source_tz` set, or `dtstart_form` of `utc`/`tzid`) is a contradiction between two statements that cannot both be true, and raises. `allow_floating=False` makes the assumption itself fatal for an operator who would rather lose an event than publish a shifted one.

**All-day.** Handled as a distinct case. A `datetime.date` is anchored at local midnight in the declared zone (`day_start_utc`), not coerced to midnight UTC, which would shift every all-day event in this registry and land a fair number on the wrong day. `start_date` / `end_date` keep the inclusive local dates so `emit` can write `VALUE=DATE` back without inverting the UTC math, and `end_utc` is the exclusive instant.

**UIDs.** `{space_id}:{source_uid}` when the source supplies one and the event is not recurring; `{space_id}:{source_uid}:{start_utc}` when it is; `sha1(space_id + start_utc + normalize(title))[:16]` when it supplies none. Recurrence is read from `IcsEvent.recurring`, which the adapter takes off the unexpanded VEVENT. `_stamp()` renders the occurrence start as `20260805T031500Z` — second precision, UTC, no varying separators — because anything that can differ between two runs churns every subscriber's calendar. `make_uid()` takes a `source_uid` string rather than an ICS component, so Maker Nexus's `YYYY-MM-DD_<amiliaId>` cache key, The Crucible's `{id}:{start_epoch}` and Meetup's `event_<id>@meetup.com` all fit unchanged; all three already carry the occurrence, so all three keep the stable two-part form.

**Address-override policy (documented).** Blank and URL-only locations are trivially safe to override. The hard case is a stale-but-plausible address, which no per-event heuristic can tell from a genuine off-site one — Sudo Room's `549 48th St` and The Box Shop's `951 Hudson Ave` are both well-formed Bay Area addresses. What separates them is a property of the *feed*: a stale house address is constant across the source, off-site venues are the exception. So `VenuePolicy` is computed once per source and the test is dominance:

- blank, or a bare URL → override
- names the space, or matches the override → override
- held by a **strict majority** of the source's located events → override
- anything else (a minority venue) → **kept**, `off_site=True`

Ties keep the source's location: the failure directions are not symmetric, since keeping a stale address is one wrong address while overriding is a wrong address on an event that was right, and it destroys the evidence that it was. Nothing is erased in any case — `location_name` always holds the source `LOCATION` verbatim and `address` holds the resolved one.

**Sanity window and quarantine.** Past (measured against the start of *today* in the source zone, not the wall clock, so a midday re-run does not delete this morning's events) and more than `MAX_FUTURE_DAYS = 730` out are dropped with a `DropReason`. Empty titles and titles over 200 characters are quarantined into a separate collection with a `QuarantineReason`, kept verbatim so the failure can be read. Drops run before quarantine — a three-year-out event with a mangled title is out of the window regardless. Every input lands in exactly one of `events`, `quarantined` or `dropped`, so "the feed shrank" always has an answer.

**Canonical event record** (`Event`, matching Part 3 of `maker-calendar-handoff.md`): `uid`, `space_id`, `source_label`, `title`, `start_utc`, `end_utc`, `tz`, `all_day`, `location_name`, `address`, `url`, `price`, `description`, `categories`, `summary_line`, `rrule`, `first_seen`, `last_seen`, `content_hash` — plus provenance the later stages would otherwise have to re-derive from the source: `source_uid`, `dtstart_form`, `tz_assumed`, `recurring`, `multi_day`, `days`, `start_date`, `end_date`, `address_source`, `off_site`, `quarantine`. `start_utc` / `end_utc` are aware UTC `datetime` objects in memory; `as_dict()` renders the ISO-8601 wire form the handoff schema describes. `content_hash` excludes the UID, the run timestamps and everything a model wrote, so re-running enrichment does not look like the source edited the event.

## Gotchas

- **`RECURRENCE-ID` is a trap and stays one.** It is present on every expanded occurrence including non-recurring ones. Any future adapter must set `RawEvent.recurring` from the unexpanded source event; setting it wrongly on a non-recurring event is not cosmetic, because it puts the occurrence start into the UID and any later change to how that start is computed would churn a UID that never needed one.
- **The floating-time assumption is a policy, not a fact.** `tz_assumed=True` marks every event whose instant was decided by this module rather than by the source. Issue 0016's health gates should treat a source that is suddenly all-assumed as a drift signal.
- **Dominance needs the batch.** `normalize_events` is deliberately batch-oriented; calling `normalize_event` per event with a default `VenuePolicy` sees a one-event feed, in which every location is trivially a majority, and will therefore override it. Per-event use is for tests and single-event sources only.
- **Sudo Room's Luma feed is the live test of the override policy.** If a future run shows `off_site=False` on an event whose `location_name` is The Box Shop, the dominance threshold has been miscomputed and real addresses are being rewritten.
- **Filters are still open.** `location_contains` and friends are issue 0010 and run *downstream* of this module. `categories` is populated with the source's own categories here, untouched, because `categories_exclude` runs on them; `enrich` (issue 0013) assigns the published taxonomy later.
- **`first_seen` is a placeholder here.** It is set to the run timestamp; the SQLite store (issue 0014) must preserve the true value when it merges on `uid`, or "new event" counts will be wrong on every run.
- **`MAX_FUTURE_DAYS` is a backstop, not the horizon.** The real clip is the adapter's 120-day window. It exists for adapters with no horizon of their own and for Sudo Room's export, which is pre-expanded to 2058.
