## Description

The repo has a registry, research notes and a design, but no code and no dependency management. Everything downstream is blocked on this.

## Expected behavior

`pyproject.toml` managed with `uv`, a `pipeline/` package with the module layout from Part 3 of the handoff, and a test runner that actually executes.

Dependencies, per the language decision in `CLAUDE.md`:

- `httpx` (HTTP/2, conditional GET)
- `icalendar` + `recurring-ical-events` (the reason this project is Python)
- `extruct` (JSON-LD, handles `@graph` / arrays / `ItemList`)
- `python-dateutil`
- `rapidfuzz` (dedupe)
- `feedgen` (RSS)
- `pydantic` (validates all local-model output)
- `PyYAML`
- `pytest`

## Actual behavior

Nothing. `python3 -c "import yaml"` required an ad-hoc install just to validate the registry.

## Notes

Directory layout to create (from the handoff, adjusted for decisions since):

```
pipeline/
  __init__.py  config.py  fetch.py
  adapters/__init__.py
  normalize.py  dedupe.py  enrich.py
  emit_ics.py  emit_rss.py  health.py  verify.py
tests/
```

`raw/`, `db/`, `out/` and `logs/` are already gitignored — create them at runtime, don't commit placeholders.

Pin dependencies. This runs unattended at 03:15 and a surprise upgrade to `icalendar` is exactly the kind of thing that would break parsing silently.

## Root cause

Nothing was ever created. The repo was design-complete — brief, registry, research notes, reference data — but held no code, no dependency manifest and no test runner, so every implementation issue (0005 onward) had nowhere to put a file and no way to prove it worked. Validating `sources.yaml` meant an ad-hoc `pip install pyyaml` outside any environment the nightly job would ever see.

## Fix

- `pyproject.toml` managed with `uv`, `requires-python = ">=3.11"`, every dependency pinned with `==` and a committed `uv.lock`. The pins are the whole point: this job runs unattended under launchd at 03:15, and a silent `icalendar` or `recurring-ical-events` upgrade breaks RRULE expansion into a green run that publishes a wrong calendar. Versions resolved and installed: httpx 0.28.1 (with the `[http2]` extra), icalendar 7.2.2, recurring-ical-events 3.8.2, extruct 0.18.0, python-dateutil 2.9.0.post0, rapidfuzz 3.14.5, feedgen 1.0.0, pydantic 2.13.4, PyYAML 6.0.3, pytest 9.1.1 (dev group).
- `pipeline/` stubbed with the layout from Part 3 of the handoff. Each module is docstring-only, but every docstring states that module's responsibility, restates the invariants it is answerable for, and names the issue that implements it — so the next agent can open one file and know the job without re-reading the brief.
- `tests/` with assertions that actually guard something, not a placeholder.
- `[tool.pytest.ini_options]` with `testpaths = ["tests"]` and `pythonpath = ["."]` so `uv run pytest` works from the repo root with no arguments.
- `raw/`, `db/`, `out/` and `logs/` deliberately **not** created. They are gitignored and belong to runtime.

## Gotchas

- **`uv` was not installed on this machine.** `which uv` came back empty, as did `uvx`, `pipx`, `mise`, `asdf`, `rye`, `poetry` and `pyenv` — Homebrew had `libuv` and `uvwasi`, which are unrelated C libraries and are easy to mistake for a hit when grepping. Installed with `brew install uv` (0.12.1) before doing anything else; without it there is no honest way to run the verification step. Worth knowing when setting up the launchd job in issue 0031: **launchd does not read the shell profile**, so the plist needs the absolute path `/opt/homebrew/bin/uv`, not a bare `uv`.
- **`uv` resolved to CPython 3.13.12, not 3.11.** `requires-python = ">=3.11"` is a floor, and uv picks the newest interpreter that satisfies it. The tests run on 3.13 today. If the mini's Python ever moves ahead of what a pinned dependency supports, add a `.python-version` file to pin the interpreter too — the dependency pins alone do not cover it.
- The counts in `tests/test_registry.py` are hard-coded from the 2026-08-05 survey. That is the intent — it is a tripwire — but it means adding or verifying a source is a two-file change: the registry and the constants at the top of that test, ideally alongside the matching `spaces/<id>.md` note in the same commit.
- Parsing `uv.lock` to read back the resolved versions is easy to get wrong: the file opens with a top-level `version = 1` key, which offsets any naive `paste`-style pairing of `name`/`version` lines by one and silently attributes every version to the wrong package. Pair them per `[[package]]` block.
