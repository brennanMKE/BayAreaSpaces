## Description

WordPress "The Events Calendar" REST API. Richer than the same site's ICS export — venue, cost, categories, organizer, ticket status — so it outranks it. Build once, reuse wherever TEC appears.

## Expected behavior

- `GET /wp-json/tribe/events/v1/events?start_date=YYYY-MM-DD&per_page=50`, paginate on `next_rest_url`.
- Unescape HTML entities in `cost` — Ace returns `&#036;20.00`.
- Keep `cost` as source text. **Do not parse to float**; "sliding scale $10–30" and "free for members" are real values.
- Map `utc_start_date`, venue, organizer, categories, `is_virtual`, ticket status onto the canonical schema.

## Notes

Currently one consumer: Ace Makerspace, 92 upcoming events over 2 pages. Verified working — the registry entry was flipped from `verified: false` to `true` once fetched, having previously been inferred from a `tec-api-version` meta tag.

**Detection heuristic for future spaces:** `?ical=1` subscribe links or `tec-api-version` in page meta means both an ICS feed and this REST API exist.

**Counter-example worth knowing:** The Crucible's pages carry `tribe-*` CSS class names but TEC is *not installed* — every `wp-json/tribe/*` route 404s. The classes are inert Avada compatibility CSS. Do not let class names talk anyone into a `tribe_rest` source.

## Root cause

Not a defect — `pipeline/adapters/tribe_rest.py` did not exist. `sources.yaml` named the adapter and `pipeline/cli.py`'s dispatch table held an unimplemented slot for it, so Ace's richest feed was reported as skipped every run and the space published through its `trust: 90` ICS fallback instead of its `trust: 100` REST one.

The part that made this more than an afternoon of `json.loads` is pagination. Ace's 92 upcoming events arrive 50 to a page, so **page 1 alone is 54% of the calendar and looks perfectly healthy** — no error, no zero, no content-type mismatch, just a calendar missing 42 events. The dispatch table also had no way to give an adapter the `Fetcher`, so an adapter that stopped at page 1 was the path of least resistance.

## Fix

`pipeline/adapters/tribe_rest.py`, shaped like `ics`/`gcal_ics`: a `parse_tribe_rest` entry point with a `parse` alias the registry name resolves to, a frozen result object, a problem enum, and nothing that raises on a bad payload.

- **Pagination follows `next_rest_url`, never a constructed `?page=N`.** TEC embeds the query it actually ran — including the `end_date` it defaulted to +2 years — in that link, and rebuilding it is another chance to request a different window than page 1 came from. Pages go through `Fetcher.fetch_url(..., label_suffix="p2")`, so they obey the same `robots.txt` decision and the same 10-second Ace rate limit, and land in `raw/` as `ace-makerspace-tribe-rest-p2.json`.
- **Three stop conditions, kept distinct.** No `next_rest_url` (the ordinary end); a 200 with `"events": []` (also the end — a feed whose count lands on the page boundary answers this way, and it is not an error); and `MAX_PAGES = 20` or a repeated URL, which is `RUNAWAY_PAGINATION` and `ok=False` rather than a quietly truncated list.
- **A failure on a later page fails the whole parse** (`PAGE_FAILED`), so issue 0014's carry-forward republishes last night's complete 92 rather than tonight's half. Half a calendar that looks healthy is the failure this project keeps designing against.
- **Every string is HTML-unescaped, and `cost` stays text.** `_clean()` runs `html.unescape` on titles, descriptions, venues, organizers, categories and cost. `&#036;20.00` → `$20.00`; "sliding scale $10-30" and "free for members" pass through byte-for-byte. Nothing converts a cost to a number anywhere in the module.
- **One intermediate shape.** `TribeEvent` subclasses `IcsEvent` and `TribeParse` subclasses `IcsParse`, so `normalize_ics`, `SourceRecord` and issue 0016's gates consume Tribe and ICS identically. TEC's extras ride along as new fields (`cost`, `currency_symbol`, `ticketed`, `is_virtual`, `featured`, `venue_name`, `venue_address`, `organizers`, `website`, `image`, `event_id`, `page`), and a `price` property carries `cost` into `Event.price` through a one-line `getattr` seam in `normalize.from_ics_event`.
- **`utc_start_date` is the authoritative instant**, converted into the event's declared `timezone` so the wall clock matches what the site displays and `dtstart_form` reads `tzid`, exactly like a TEC ICS `DTSTART;TZID=`. Fallbacks: `start_date` + zone, then floating. Nothing naive can leave the module. All-day events keep TEC's already-**inclusive** end — no RFC 5545 exclusive-`DTEND` correction, which is the opposite of the ICS adapter and is asserted.
- **"HTTP 200 is not success", in this endpoint's dialect.** Status first (non-2xx is `HTTP_ERROR`), then content type (`text/html` is `WRONG_CONTENT_TYPE`; `text/plain` is tolerated *only* when the body is really JSON), then the body sniff (`NOT_JSON`), then the *shape* — valid JSON with no `events` array is `NOT_TRIBE`, because WordPress's `rest_no_route` error object is perfectly good JSON and an adapter returning `[]` for it would be indistinguishable from a space with nothing on.
- **`pipeline/cli.py`: `AdapterEntry.paginates`.** `process_source` hands `fetcher` and `ref` to adapters that declare it. `tribe_rest` is the only one today; nothing else changes shape.
- **`horizon_days` clipping is explicit**, since there is nothing to expand: `vevent_count` is what pagination decoded, `event_count` is what survived the window. Ace's `end_date` default of +2 years makes that a real filter, not a formality.

## Gotchas

**`tribe-*` class names are not evidence.** The Crucible's pages are full of them and The Events Calendar is not installed — they are inert Avada theme compatibility CSS, shipped whether or not the plugin is present, and every `wp-json/tribe/*` route there 404s. The counter-example is written into the module docstring *and* attached to the 404 message itself, so a future reader meets it at the moment they would otherwise be tempted. The check that settles it is one `curl` against the events route.

**The detection heuristic that does work:** a `?ical=1` subscribe link, or `tec-api-version` in the page meta. That means both an ICS feed and this REST API exist — register both, REST at the higher trust, and never ingest them as two independent sources.

**Page 1 is a plausible-looking calendar.** 50 of 92 events, no error, no zero, nothing for a count gate to catch except a 46% drop the first time it happens. This is why pagination lives in the adapter rather than being left to a follow-up, why a later-page failure fails the whole parse, and why `AdapterEntry.paginates` exists at all.

**A 200 with an empty `events` list is the end of a feed, not an error** — and `RUNAWAY_PAGINATION` is the opposite case. Conflating them would either truncate a legitimate feed or loop the nightly run forever, so they are separate branches with separate tests.

**TEC's all-day `end_date` is already inclusive** (`00:00:00` → `23:59:59` local), the reverse of iCalendar's exclusive `DTEND`. Applying the ICS adapter's `-1 day` correction here would silently shorten every multi-day event by a day.

**`cost` and `cost_details` disagree by design.** `cost_details.values` is `["20.00"]` for a priced event and `[]` for "sliding scale $10-30" — which is exactly the temptation to reach for the "structured" field and produce `None` for the events whose price actually needed explaining. Only `cost` is carried; `currency_symbol` is kept for diagnostics and is documented as not being a route back to a number.

**The two Ace sources deliberately do not share a UID.** REST uses TEC's `global_id` (`www.acemakerspace.org?id=40101`); the ICS export uses `{postid}-{start}-{end}@host`. Making them collide on `uid` would hide the overlap from issue 0015's dedupe, which is the stage that is supposed to resolve it on `trust` (100 vs 90) and is tested doing so.
