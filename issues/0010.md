## Description

Filters applied after parse, before dedupe. The reason this is its own issue rather than a footnote: **filters drop events silently**, which makes them the same class of hazard as a wrong feed URL.

## Expected behavior

Support `location_contains`, `title_contains`, `location_excludes`, `title_excludes`, `categories_exclude`, and `location_allow_when_missing`.

**`location_allow_when_missing` defaults to keeping the event.** 15% of Frontier Tower's events set `LOCATION` to a bare `luma.com/event/…` URL when the host hides the address — including real makerspace events. Any `location_contains` filter that treats those as non-matching deletes them with no error and no way to notice.

Log every drop with the rule that caused it, at least at debug level. A filter that silently removes 90% of a feed should be visible in one grep.

## Notes

Real filters in the registry today, all derived from observed values rather than guessed:

- Frontier: keep `Frontier Tower` / `995 Market` / `Berlinhouse`; exclude titles `Hold -`, `TBA (`, `Placeholder`. The originally-guessed filter (`Makerspace`, `Arts and Music`, `Robotics`) matched **9 of 262 events** — `Arts and Music` never appears, it is `Arts & Music`.
- Maker Nexus: `title_excludes: ["(Equipment Training)"]`. Without it, 76 distinct safety-checkout titles across 171 instances swamp every other space.
- Sudo Room: `categories_exclude` for cross-posted third-party events.
- Humanmade: `title_contains: ["@ Humanmade"]` on a partner calendar whose `LOCATION` is unpopulated.

Match against HTML-escaped values where the source stores them escaped — The Crucible's blob has `Glass Fusing &amp; Slumping`, never `&`.

## Root cause

Not a regression — the stage did not exist. Normalize (issue 0009) deliberately left the
registry filters downstream, and `Filters` in `config.py` was a validated model with nothing
reading it. What made this a separate issue rather than a footnote is that a filter is the
one stage whose failure mode is *silence*: a wrong pattern produces a smaller calendar, never
an error, and the measured example is in `spaces/frontier-makerspace.md` — the originally
guessed Frontier filter (`Makerspace` / `Arts and Music` / `Robotics`) kept 9 of 262 events,
because `Arts and Music` never appears in that feed; it is `Arts & Music`.

A second, latent bug was found while implementing: `Filters.location_allow_when_missing`
defaulted to `False`, directly under a comment saying it should default to keeping. That
default would have made every future `location_contains` entry silently delete the 40 of
Frontier Tower's 262 events (15%) whose `LOCATION` is a bare `luma.com/event/…` URL —
including `LASER FRYDAYS: Laser Cutter Training`, `Frontier Makerspace All-Hands & Demo
Night` and `The SF Bay Area LeRobot Hackathon`, three of the most maker-relevant events on
the calendar.

## Fix

New `pipeline/filters.py`, applied after normalize and before dedupe.

**Public API.** `apply_filters(events, filters, *, space_id="", source_label="")` and
`filter_normalization(normalization, filters)` both return a `FilterResult`, which iterates
and `len()`s as the kept events (same shape as `Normalization`) and additionally carries
`dropped: tuple[Filtered, ...]`, `drops_by_rule`, `hits_by_pattern`,
`kept_on_missing_location` and `summary()`. Supporting predicates `matches`, `first_match`,
`all_matches`, `category_matches` and `location_state` are public because the registry's
matching semantics are the thing most worth testing directly. Enums: `FilterRule`
(`title_excludes`, `location_excludes`, `categories_exclude`, `title_contains`,
`location_contains`, `location_missing`) and `LocationState` (`present`, `empty`,
`url_only`).

**Per-rule counts, for `health.json` (issue 0017).** `drops_by_rule: dict[str, int]` has one
entry for every *configured* rule even when it fired zero times, and `location_missing` is
split out from `location_contains` because "dropped for having no address" and "dropped for
having the wrong address" have different fixes. Each dropped event is attributed to exactly
one rule, so `sum(drops_by_rule.values()) == dropped_count`. `hits_by_pattern:
dict[str, dict[str, int]]` counts, per pattern, how many events it matched — every matching
pattern gets credit, not just the one the drop was charged to, so an overlapping-but-valid
pattern (`Berlinhouse` inside `Frontier Tower | Berlinhouse, …`) is not mistaken for a dead
one. A zero there is the `Arts and Music` typo, and `dead_patterns` surfaces it.
`summary()` returns `{space_id, source_label, input, kept, dropped, drop_rate, by_rule,
by_pattern, kept_on_missing_location, dead_patterns}`, all JSON-ready.

**What "missing" means.** Filters match `Event.location_name` — the source's verbatim
`LOCATION` — and never `Event.address`. When those two differ, `address` is the registry's
own `address_override` (issue 0009), and matching our own override against our own filter is
circular: on Humanmade's partner calendar or Hacker Dojo's Meetup feed, which carry no
`LOCATION` at all, `location_contains: ["Humanmade"]` would match every event and the filter
would silently become a no-op that looks like it is working. So `missing` is a property of
the source's text only: `empty` (absent or blank) or `url_only` (a bare URL, using the same
`is_bare_url` normalize uses, now public so the two stages cannot drift). An event whose
`LOCATION` is real but whose *address* was overridden is `present` and is matched normally.
Both missing states are governed by `location_allow_when_missing` but are reported
separately in the log line and the drop record.

**Default corrected.** `Filters.location_allow_when_missing` now defaults to `True`, per the
CLAUDE.md invariant. Registry entries that mean the strict behavior still write
`location_allow_when_missing: false`.

**Matching semantics, documented in the module docstring and in `sources.yaml`.**
Case-insensitive substring — no globbing, no regex, no word boundaries — and entity-insensitive
in both directions: each value and each pattern is compared as written *and* HTML-unescaped, so
`Glass Fusing & Slumping`, `Glass Fusing &amp; Slumping` and the mixed forms all match the
same events. Unescaping happens only for comparison, so the record stays verbatim. An empty
pattern never matches, since an empty string is a substring of everything. Order of
judgement is excludes (title, location, categories) then keep-lists (title, location); the
first rule to fire owns the drop.

**Visibility.** Every drop logs at `DEBUG` with the rule and pattern, tagged `filter drop`
(one grep). A run summary logs at `INFO`, or at `WARNING` when a filter set removes ≥90% of a
feed of ≥5 events. Dead patterns log at `INFO` with the `Arts and Music` example in the
message. An empty `Filters` logs nothing and keeps everything. Quarantined events are not
filtered — they are already withheld, and hiding a broken extraction behind a filter defeats
the point of holding it.

## Gotchas

- **The default flip is a behavior change for one existing registry entry.** Frontier's
  biopunk partner calendar has `location_contains` with no explicit
  `location_allow_when_missing`, so it now keeps its blank/URL-only-location events instead of
  dropping them. That is the invariant working as intended — keeping a possibly-off-site event
  is visible in the published calendar and recoverable; dropping a real one is neither — but
  it is a real change and `kept_on_missing_location` in `health.json` is where to watch it.
- **`hits_by_pattern` does not sum to a drop count.** It is a diagnostic (does this string
  appear in this feed at all?), not accounting. `drops_by_rule` is the accounting and it does
  sum, exactly.
- **A dead pattern is not proof of a typo.** A legitimate `title_excludes` often has nothing
  to exclude tonight. On a *keep*-list, though, a zero is the first thing to check when a
  space goes quiet.
- **Entity-insensitivity does not forgive a wrong word.** `Arts and Music` still does not
  match `Arts & Music`, and a test pins that: unescaping must not become fuzzy matching, or
  the failure this issue documents would be hidden rather than fixed.
- **Filters run per source, before dedupe.** Once feeds are merged there is no way to tell
  which source's filter block applies, so `filter_normalization` is the seam and issue 0012's
  CLI must call it inside the per-source loop.
