## Description

The local working store at `db/events.sqlite`. Per `CLAUDE.md`, SQLite holds everything that is per-run bookkeeping; Postgres on EC2 holds only the published result.

## Expected behavior

Tables for:

- **Per-source HTTP state** — `etag`, `last_modified`, `last_status`, `last_success_at`, `consecutive_failures`, `last_content_hash`. Drives conditional GET.
- **Event history** — every event by `uid`, with `first_seen`, `last_seen`, `content_hash`. `first_seen` is what RSS `pubDate` uses (issue 0018) and what carry-forward restores.
- **Run history** — per-run, per-source counts, latency, HTTP status, gate outcomes. Needed for night-over-night comparisons and for `require_nonzero_once`.

## Notes

`first_seen` must survive an event's content changing. If a space edits a title, that is not a new event, and a subscriber should not be re-notified.

`require_nonzero_once` (Humanmade's Eventbrite, Hacker Dojo's Luma) needs persistent state — the pipeline has to remember that a source has *never* returned events, which is a different condition from "returned zero tonight".

Keep the schema boring. This is a cache and an audit trail, not the product.

## Root cause

Not a regression — the store had never been built. Issue 0006 defined `HttpStateStore` as a
protocol and shipped `InMemoryStateStore` as the default, which forgets every `ETag` when the
process exits. Since the nightly job *is* a process that exits, conditional GET was structurally
dead: every run re-downloaded every feed unconditionally, including the two that are 8 MB and
11 MB. Event history and run history did not exist at all, so `first_seen`, carry-forward and
`require_nonzero_once` had nothing to read.

## Fix

`pipeline/store.py`, a `Store` class over stdlib `sqlite3` at `db/events.sqlite` (path from
`pipeline.config.DB_DIR`, created on demand because `db/` is gitignored and absent on a fresh
checkout). No new dependency.

**Per-source HTTP state.** `Store.get`/`Store.put` implement `HttpStateStore` structurally, so
`isinstance(store, HttpStateStore)` holds and `fetch.py` needed no change at all. The
`source_state` table's columns are `SourceState`'s field names verbatim — `etag`,
`last_modified`, `last_status`, `last_success_at`, `last_seen`, `consecutive_failures`,
`last_content_hash` — keyed on `source_key` = `{space_id}:{label}`.

**Event history.** `record_events()` merges on `uid` and returns an `EventMerge` classifying
each event as new, changed or unchanged, with the events themselves reconciled to carry the
*stored* `first_seen` rather than the run timestamp normalize put there. The serialized
`Event.as_dict()` is stored as JSON alongside the columns, and `event_from_dict()` is its
inverse, which is what lets `carry_forward_events()` republish a failed source's last-known-good
set instead of dropping a space out of the calendar. That set is the events from the most recent
run that actually produced any — not the union of everything ever seen, which would resurrect
events the source deliberately removed.

**`first_seen` is written once and never again.** The `UPDATE` path deliberately omits the
column; only the `INSERT` path sets it. A title edit moves `content_hash` and `last_changed_at`
and nothing else.

**Run history.** `start_run` / `record_source_run` / `finish_run`, with `record_run()` as a
one-call convenience over a `RunReport`. `raw_count` and `horizon_count` are stored separately
because CLAUDE.md is explicit that the first says almost nothing. Gate outcomes are per-source
(`gate_blocked`, `gate_reasons`, settable after the fact via `set_gate_outcome`) and per-run
(`health_blocked`, `health_reasons`). `source_history()` returns a source newest-first across
runs, which is issue 0016's night-over-night input.

**`require_nonzero_once`.** A `source_milestone` row records `first_nonzero_at` the first time a
source produces events, from either `record_events()` or `record_source_run()`.
`has_ever_returned_events(space_id, label)` is the first-class query, and it stays `True` through
a zero night. `sources_never_nonzero(keys)` reports the waiting ones.

**Migrations.** A `schema_version` table and a `{target: migration}` dict applied in order from
whatever version was found. Idempotent — reopening finds nothing to apply. A database at a
*higher* version than the code raises `SchemaTooNewError` rather than reading a schema it only
half understands, because failing at 03:15 is cheaper than corrupting silently.

**Timezones.** Everything is stored as an ISO-8601 UTC string via `to_iso()`, which raises
`NaiveDatetimeError` on a naive datetime instead of guessing a zone. `from_iso()` refuses a row
that was somehow stored without one. A naive value in a cache is worse than one in a
calculation, because it is still wrong six months later.

`cli.py` is not wired to the store yet — that belongs to 0014 (carry-forward) and 0016 (gates),
which are the callers that give the tables a reason to be written.

## Gotchas

**`first_seen` is written by `INSERT` only.** The merge deliberately uses an explicit
`INSERT`/`UPDATE` branch rather than an upsert, because `ON CONFLICT DO UPDATE` makes it far too
easy to write `first_seen = excluded.first_seen` in a later edit and silently re-notify every
subscriber. The `UPDATE` statement does not mention the column at all.

**Carry-forward keys on `MAX(last_seen)`, so every event in one `record_events()` call must
share a timestamp.** It does — the batch computes `now` once. Calling `record_events()` twice
per run for the same source with different timestamps would split the last-known-good set.

**`sqlite3` NOT NULL and upserts.** `last_changed_at` is `NOT NULL`, which is another reason the
merge branches explicitly: passing `NULL` in the insert tuple of an upsert to mean "keep the
existing value" is not reliably safe.

**The store is not yet wired into `cli.py`.** Nothing writes `db/events.sqlite` during a real
run until issue 0014 passes a `Store` to the `Fetcher` and records the report. Conditional GET
is *implemented and proven* but not *live* until that one line lands.

**A source at zero forever is a waiting state, not a failure.** `has_ever_returned_events()`
returning `False` for Humanmade's Eventbrite is the correct answer, not a bug in the store.
