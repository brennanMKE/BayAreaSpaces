# 0013 — SQLite working store for ETags, event history and run state

## Description

The local working store at `db/events.sqlite`. Per `CLAUDE.md`, SQLite holds everything that is per-run bookkeeping; Postgres on EC2 holds only the published result.

## Expected behavior

Tables for:

- **Per-source HTTP state** — `etag`, `last_modified`, `last_status`, `last_success_at`, `consecutive_failures`, `last_content_hash`. Drives conditional GET.
- **Event history** — every event by `uid`, with `first_seen`, `last_seen`, `content_hash`. `first_seen` is what RSS `pubDate` uses (issue 0018) and what carry-forward restores.
- **Run history** — per-run, per-source counts, latency, HTTP status, gate outcomes. Needed for night-over-night comparisons and for `require_nonzero_once`.

## Notes

`first_seen` must survive an event's content changing. If a space edits a title, that is not a new event, and a subscriber should not be re-notified.

`require_nonzero_once` (Humanmade's Eventbrite, Hacker Dojo's Luma) needs persistent state — the pipeline has to remember that a source has *never* returned events, which is a different condition from "returned zero tonight".

Keep the schema boring. This is a cache and an audit trail, not the product.
