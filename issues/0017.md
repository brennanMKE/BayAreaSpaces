## Description

Per-run diagnostics written every run, whether or not publication proceeded. This is the file the repair workflow reads.

## Expected behavior

`out/health.json` with, per source: HTTP status, content type, bytes, raw record count, post-expansion horizon count, previous-night count, latency, gate verdict, whether events were carried forward and how stale they are, and `LAST-MODIFIED` age where the source exposes it.

Plus run-level: total events, per-space totals, gate outcomes, whether the LLM stages ran, and start/end timestamps.

## Notes

The key downstream consumer: when a source shows 0 for three consecutive nights, that adapter has drifted and the OpenCode repair pass gets dispatched against that one space — with `raw/` from those nights as the diff material.

Make it easy to answer "did the source change or did we?" in ten seconds. That question is the whole reason `raw/` is retained.

Keep it stable and machine-readable; the website project may eventually surface a status page from it.

## Root cause

Nothing was wrong — this is the file that had never been written. Issues 0012–0016 built every number it needs and each of them left a `summary()` or an `as_dict()` behind pointing at this issue, but the run ended without serializing any of it. The three consequences:

- **A blocked run left nothing to read.** The health gates exit early from `run_pipeline` before the emit step, so the one night whose diagnostics matter most produced a log line and an exit code.
- **The repair trigger was not answerable.** CLAUDE.md dispatches an OpenCode pass when a source shows 0 for three consecutive nights, and the run history was in SQLite behind a query nobody had written. `raw/` retained the evidence but nothing recorded which file belonged to which night.
- **The per-source verdict and the per-source record were separate lists.** `SourceRecord` knows what a source returned; `SourceVerdict` knows what the gates made of it. Joining them by `space_id:label` was left to whoever read the run.

## Fix

New `pipeline/health_json.py` composes and writes the document; `run_pipeline` calls it on **both** exit paths, blocked and clean, after `finished_at` is set and before the run row is closed.

**Composition, not re-derivation.** The document is built on top of `RunReport.as_dict()` and lifts two lists out of it — the source records and the gate verdicts — welding them into one row per source. `FilterResult.summary()`, `DedupeResult.summary()` and `EmitResult.summary()` are carried verbatim. Nothing is recounted here.

**The three-night condition is a read, not an analysis.** `Store.zero_streak()` returns the unbroken streak of nights a source answered 0, newest first, each row carrying its `raw_path`. Tonight comes from the live record and the rest from the store, so a `--dry-run` — which never writes a row — does not report a streak one night short on the very invocation someone is using to investigate. Every source carries `consecutive_zero_nights` and `repair_ready`; the document carries `repair.candidates` with the raw paths of those nights attached, which is the OpenCode command's argument list.

**Only `ok` nights are judged.** `skipped` (adapter still an open issue) and `blocked` (`robots.txt` said no) are zero by decision and would otherwise report every pending adapter as drifted on night three forever; `failed`/`error` are carry-forward's clock and counting them here would dispatch a repair pass at an outage; `not_modified` has no body to count and a 304 means the server says the source is current, which is the opposite of drift.

**Ten seconds.** `raw_path` is on every source record and on every repair candidate, because "did the source change or did we?" is a `diff` and finding the file is most of the ten seconds.

Supporting changes:

- Store schema **v2**: `run_source.raw_path`, added by migration rather than by editing v1. An existing v1 database upgrades in place.
- `SourceRecord.filters` carries `FilterResult.summary()` — the per-rule and per-pattern accounting. `filtered_out_count` says 253 of 262 events went; only this says which rule did it and which configured pattern matched nothing, and the Frontier `Arts and Music` bug is visible only as a zero.
- `RunReport.health_json_path` / `health_json_error`, and a line in the run report. A write failure is logged and recorded, never fatal: the calendar is already published by then and losing diagnostics is the smaller loss.
- `--dry-run` and `--space` write to `out/.staging/health.json`, following the staging decision `run_pipeline` already makes rather than making it a second time.
- Written through `emit_ics.write_atomic` — same temp file plus `os.replace` as the ICS emit, so a status page polling the file sees the old document or the new one, never a prefix.

Top-level shape (`"schema": 1`): `schema`, `pipeline_version`, `generated_at`, `path`, `repair`, `run`, `totals`, `llm`, `gates`, `sources`.

## Gotchas

- **`horizon_count == 0` does not mean "returned nothing".** On a 304 there is no body to count and the events come from `carry_forward_count`; on a `skipped` source there was no fetch at all. Anything reading counts out of this file has to read `status` with them, which is why `zero_streak` judges only `ok`.
- **Tonight's row is already in the store when the gates run**, so the streak query takes `exclude_run_id` and the caller folds in the live record. Reading tonight from both would count it twice.
- **`totals.by_space` comes from the event set, not from `emit`.** A blocked run has no emit summary, and that is the run whose per-space totals someone most wants.
- **The document embeds `RunReport.as_dict()` under `run`**, so a new field on the report appears in `health.json` automatically. That is the intent, but it means a field named after something transient (a path, a machine) leaks into a file the website may serve.
- **`raw_path` is null when there was no body** — a 304, a skipped source, a blocked source. The repair candidate's `raw_paths` list is therefore shorter than its `consecutive_zero_nights` in the general case.
- **`schema` is 1 and adding a key is not a break.** Bump it when a key changes meaning or disappears, not when the document grows.
