## Description

When a source fails, its events from the previous successful run must be republished rather than dropped. A transient 503 must never silently delete a space from the calendar.

## Expected behavior

- On failure after retries: mark the source `failed`, load its last-known-good events from SQLite, and emit those.
- Carried-forward events are flagged in `health.json` with the age of the data.
- After N consecutive nights of failure (suggest 3, matching the repair trigger in `CLAUDE.md`), escalate to an alert rather than carrying forward indefinitely.
- Carry-forward must respect the horizon: yesterday's events that have since fallen out of the window still drop out.

## Notes

Interacts with the health gates (0016). Carry-forward is what makes a `failed` source safe; the gates are what stop a *successful* source that returned garbage. Both are needed and they are not the same mechanism.

Three consecutive zero nights is also the trigger for the OpenCode repair workflow — an adapter has drifted, and the raw payloads from those nights are the diff material.

## Root cause

Two separate gaps, and they had to be closed together.

**Carry-forward did not exist.** `process_source` returned an empty event list for a `failed` source and the run loop simply added nothing, so a single 503 removed a space from the published calendar for a night. `Store.carry_forward_events()` had been written by issue 0013 in anticipation of this and had no caller.

**The store was not wired in.** Issue 0013 built `Store` and proved `fetch.py` worked against it, but `run_pipeline` still constructed `Fetcher(registry, transport=…, raw_dir=…)` with no `state=`, so the fetcher fell back to `InMemoryStateStore` and forgot every ETag when the process exited. Conditional GET was inert: Sudo Room's 8 MB feed and Maker Nexus's 11 MB feed re-downloaded in full every night to compute a byte-identical answer. Nothing was written to `db/events.sqlite` at all — no HTTP state, no event history, no run rows — which is also why carry-forward had nothing to read from.

Turning the second one on without the first would have been worse than leaving both off: with validators stored, sources start answering `304 Not Modified`, a 304 carries no body, the adapter correctly returns zero events, and every *unchanged* space would have vanished from the calendar. The optimization would have caused the exact failure this project keeps designing against.

## Fix

New `pipeline/carry_forward.py`, plus wiring in `pipeline/cli.py` and two additions to `pipeline/store.py`.

**What carries forward, and what does not.** `failed` and `error` republish the last-known-good set. `blocked` and `skipped` never do, and they are named in `NEVER_CARRY_FORWARD` rather than left to the absence of a branch. `blocked` is the load-bearing one: `robots.txt` forbade the fetch, and republishing a stale copy is working around the file by another route, which CLAUDE.md rules out explicitly. `skipped` is a decision somebody made in the registry, and reviving its events would undo it. `error` is included because an unhandled exception in *our* parser on *one* feed is a bug in us, not evidence that a space cancelled everything — issue 0012's run loop already said so in a comment.

**The horizon still applies.** Republished events go back through the same window the adapter would have clipped them to: the floor is the start of today in the source's zone, the ceiling is `horizon_days` out, and all-day events stay current through their last day. A carried-forward calendar therefore decays — last night's class that has since happened drops out on its own.

**Age, and escalation at three nights.** The record carries `carried_forward`, `carry_forward_count`, `carry_forward_age_seconds` / `_days`, `last_known_good_at`, `consecutive_failures`, `escalated` and `alert`, all of them in `as_dict()` for issue 0017. At `ESCALATE_AFTER_NIGHTS = 3` — matching the repair trigger in CLAUDE.md — carry-forward *stops* and the alert is set instead. The invariant survives that, because it is about silence: nights one and two are silent and carried, night three is loud. By then the data is three days old and the horizon has been eroding it nightly; what is left is a ghost calendar.

**Counting the failures honestly.** `SourceState.consecutive_failures` is incremented by the fetch layer and reset by a successful *transport*, so a feed answering 200 with the homepage every night — "a wrong adapter is as silent as a wrong URL" — would sit at zero forever. New `Store.consecutive_failed_runs()` counts `failed`/`error` rows backwards through the recorded run history, excluding dry runs, and `consecutive_failures()` takes the larger of the two.

**A 304 is not carry-forward.** It replays the same rows, under a different name (`reused_unchanged`, `CarryReason.NOT_MODIFIED`). No age is held against it, no failure counter moves, nothing escalates, and `event_count` / `horizon_count` are set to the reused count so issue 0016 does not see a "went to zero" on the one outcome that is defined as nothing changing. The ICS adapter already said as much in the error string it returns for a 304.

**The store, wired.** `run_pipeline` opens it, passes it as `Fetcher(state=store)`, calls `record_events()` **once per source per run** (the contract `carry_forward_events()` depends on, since it keys on `MAX(last_seen)`), records each source with `record_source_run()`, and brackets the whole thing with `start_run()` / `finish_run()`. `record_run()` is deliberately not used: it creates the run row at the end, and the events need a `run_id` while the run is still going. The merged events from `record_events()` replace the raw ones in the report, so they carry the *stored* `first_seen` — issue 0018 reads that as RSS `pubDate`.

**`--dry-run` policy: read everything, write nothing.** A dry run fetches through the new `ReadOnlyStore`, so stored ETags are used and the run is realistic and cheap, and every write is dropped: no HTTP state, no events, no run row. The other policy — record the HTTP state, since a validator is only a cache — was considered and rejected. Storing an ETag hands the **next real run** a 304 for a body this process parsed and then threw away, so the published calendar would be assembled from replayed history because a debugging invocation spent the only unconditional fetch. `--dry-run` is precisely the tool you reach for when a source is misbehaving, and a diagnostic that mutates the state under diagnosis is a trap. The same argument covers the failure counter: a dry run must never be able to push a source toward its third strike and fire an alert. `ReadOnlyStore.put()` is a silent no-op because the fetch layer calls it on every request; the higher-level writers raise, so a guard that quietly stops working becomes a failed dry run rather than a polluted database.

`run_pipeline` defaults to an **in-memory** store when neither `store=` nor `db_path=` is given — the pre-0014 behavior. `main()` passes `DEFAULT_DB_PATH`, so the nightly job persists; a test or an experiment that forgot to name a database cannot silently write into the real one.

## Gotchas

**Turning on conditional GET is not a free optimization.** A 304 has no body, the adapter returns zero events, and without the replay path every unchanged space would have dropped out of the calendar the night this shipped. Anyone touching the store wiring should keep the 304 branch and its test.

**`record_events()` is once per source per run, and it is load-bearing.** `carry_forward_events()` selects the rows sharing `MAX(last_seen)`. A second call for the same source in the same run splits that night's set across two timestamps, and tomorrow's carry-forward republishes only the tail — a partial calendar that looks like a working feed.

**Carry-forward after a failure deliberately does not re-record.** The age has to keep growing until somebody looks. Re-stamping would make a dead source look alive forever and would pollute the `require_nonzero_once` milestone. The 304 path *does* re-record, because the server affirmed the bytes are current.

**A carried-forward source reports `event_count == 0`.** The events reach the calendar, but the source produced none tonight, and issue 0016's gates must see the failure rather than the bridge over it. The republished number lives in `carry_forward_count`.

**The horizon floor is local midnight, not `now`.** At 03:15 UTC it is still the previous evening in California, so an event's "did it fall out of the window" answer is not what a UTC-day intuition predicts. The test fixture spells the boundary out as a constant for exactly this reason.

**`main()` now writes to `db/events.sqlite` by default.** Any test or script driving `main` must pass `db_path`, or it will share state with the real nightly run — including its ETags, which means answering 304 to itself.
