# 0014 — Carry-forward on source failure

| | |
|---|---|
| **Status** | open |
| **Module** | fetch / health |
| **Platform** | macOS |
| **First seen** | 2026-08-05 |

## Description

When a source fails, its events from the previous successful run must be republished rather than dropped. A transient 503 must never silently delete a space from the calendar.

## Expected behavior

- On failure after retries: mark the source `failed`, load its last-known-good events from SQLite, and emit those.
- Carried-forward events are flagged in `health.json` with the age of the data.
- After N consecutive nights of failure (suggest 3, matching the repair trigger in `CLAUDE.md`), escalate to an alert rather than carrying forward indefinitely.
- Carry-forward must respect the horizon: yesterday's events that have since fallen out of the window still drop out.

## Notes

Interacts with the health gates (0016). Carry-forward is what makes a `failed` source safe; the gates are what stop a *successful* source that returned garbage. Both are needed and they are not the same mechanism.

Three consecutive zero nights is also the trigger for the OpenCode repair workflow — an adapter has drifted, and the raw payloads from those nights are the diff material.
