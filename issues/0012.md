## Description

`python -m pipeline run` — one deterministic process that iterates `sources.yaml` and does everything. No agent in the loop.

## Expected behavior

```
python -m pipeline run [--dry-run] [--space <id>] [--no-llm] [--horizon-days N]
```

- Loops spaces one at a time; sequencing falls naturally out of per-host rate limiting and costs nothing.
- `--dry-run` writes to `out/.staging/` and skips publishing.
- `--space <id>` runs a single space — the workhorse for adapter development and for the repair workflow.
- `--no-llm` skips the enrich stage entirely.
- **If LM Studio is not answering on `localhost:1234`, skip the model stages and emit Tier A/B rather than failing the run.** Structured data must never be hostage to the model being up.
- Exit non-zero when health gates block publication, so launchd logs show it.

## Notes

Pipeline order: fetch → adapters → normalize → filter → dedupe → enrich → health gates → publish.

Expected wall-clock is minutes. The run is dominated by deliberate waiting (2s per host, 10s for Ace), not compute — which is exactly why goroutines would have bought nothing and why Python was the right call.

Structured logging per source: status, content type, bytes, raw count, post-expansion horizon count, elapsed. That record is what `health.json` (issue 0017) is built from.

## Root cause

Not a defect — the missing top of the pipeline. Issues 0004–0011 built the parts (registry, fetch, `ics`, `gcal_ics`, normalize, filters, emit) and nothing wired them together, so the project could parse a feed in a test but could not produce a calendar. This issue is the `for` loop that CLAUDE.md's "The nightly run" describes, and it completes Phase 1.

## Fix

`pipeline/cli.py` plus a three-line `pipeline/__main__.py`.

**The surface**

```
python -m pipeline run [--dry-run] [--space <id>] [--no-llm] [--horizon-days N]
python -m pipeline validate
```

Both accept `-v/--verbose` (DEBUG instead of INFO) and `--version`. Logging goes to stderr, the report to stdout, so launchd captures both without them interleaving into nonsense.

**Dispatch.** `ADAPTERS` maps each of the ten registry adapter names to an `AdapterEntry(name, issue, parse)`. `ics` → issue 0007, `gcal_ics` → 0008; the other eight carry their issue and no parser, and a source naming one is recorded `status="skipped"`, `skipped_because="adapter_not_implemented"` with the message *"adapter 'json' is not yet implemented, see issue 0022"*. `TODO` sources skip the same way (`skipped_because="todo"`, issue 0002), as do `enabled: false` entries. All 30 registry sources appear in the report, not the 26 that run — "the registry has 30 and the run mentioned 26" is a question that should never need asking.

Both implemented adapters are reached through `Fetcher.fetch(ref)` rather than through `fetch_gcal_ics`, because `resolve_url()` already delegates the `calendar_id` → URL construction to `gcal_ics`, and going through the common path keeps the `FetchResult` (content type, bytes, timings) that the structured record needs.

**The record.** `SourceRecord` carries the six fields the issue names — `status`, `content_type`, `bytes`, `raw_count`, `horizon_count`, `elapsed_seconds` — plus attempts, redirects, `raw_path`, rate-limit wait, `last_change`/`stale_days` for `max_stale_days`, and a count per stage (`normalized_count`, `dropped_count`, `quarantined_count`, `filtered_out_count`, `tz_assumed_count`, `event_count`). It is emitted as data: `extra={"source_record": record.as_dict()}` on the log record, and `RunReport.as_dict()` is the whole run in JSON-ready form. Issue 0017 should take that verbatim rather than re-deriving it. `raw_count` and `horizon_count` are deliberately separate — Sequoia Fabrica ships 89 VEVENTs for ~7 live events.

**`.env`.** `parse_env_file` / `load_dotenv` — about twenty lines, no dependency. Loaded before `load_registry`, and **never overrides a name already in the environment**, so `FOO=bar python -m pipeline run` does not lie and issue 0031's plist can set values that win. Missing file is normal and silent.

**LM Studio.** `probe_lm_studio()` GETs `/models` with a 2 s timeout and answers `False` for every failure mode. Not available → log it, skip the model stages, emit Tier A/B. `--no-llm` skips the probe entirely. Enrich itself is issue 0029, so the current outcome is a skip either way — but the decision, the reason and the log line are real now.

**Exit codes.** `EXIT_OK=0`, `EXIT_HEALTH_BLOCKED=1`, `EXIT_CONFIG=2`, `EXIT_ERROR=3`. `evaluate_health()` is the issue-0016 seam: it returns `HealthDecision(blocked=False, implemented=False)`, and the branch that returns `EXIT_HEALTH_BLOCKED` and skips the publish is already wired and tested by patching the seam. `implemented=False` rides into `health.json` so the absence of gates is stated rather than looking like a pass.

**Two refusals to publish, neither of them a health gate.** A `--space` run always writes to `out/.staging/` — its event set is by construction one space's worth, and writing that to `out/calendar.ics` would replace the merged calendar with a tenth of itself. And a run producing zero events does not write at all: the only thing an empty calendar can do to a subscriber is delete theirs.

**`validate`.** Loads the registry and prints the user agent, horizon, per-adapter counts with implemented/pending and the issue number, and a per-space source list flagged `disabled` / `TODO (issue 0002)` / `adapter pending (issue NNNN)` / `unverified`. No network anywhere in the path, which is what makes it usable while issue 0001 is open.

## Gotchas

- **A duplicate UID would have aborted the entire night's publish.** `emit_ics` refuses a calendar containing two VEVENTs with one UID, and it is right to — a client treats one UID as one event, so the duplicate silently loses an occurrence. But the refusal is fatal to the whole run: one space syndicating one event through two of its own feeds would take the other ten spaces off the calendar with it. Real dedupe is issue 0015; `collapse_uid_collisions()` is the floor beneath it — first in registry order wins, every collision logged by UID and carried in `RunReport.uid_collisions` as material for 0015. This surfaced as a test failure and is not hypothetical.
- **`--space` silently publishing a partial calendar is the obvious footgun here**, and the reason single-space runs are forced to staging. Anyone adding a `--publish` override should think hard about it first.
- **A zero-event run writes nothing.** That is not a health gate and must not be mistaken for one — it is a refusal to overwrite a good file with a deletion. Issue 0016 still needs the real gates; `evaluate_health()` reports `implemented: False` precisely so nobody reads a clean run as a checked one.
- **Filters are visible in the test counts, on purpose.** Three of the thirteen runnable sources carry a `location_contains` filter the test fixture's Oakland address does not match, so a full mocked run emits 10 events and not 13. `test_dry_run_publishes_every_runnable_source` asserts the drop explicitly rather than hardcoding 13 — filters drop events silently, and the count moving is the only warning you get.
- **A per-source failure never ends the run.** `process_source` catches everything, including `NaiveDatetimeError`; the invariant is still absolute for the record it protects, but one feed violating it must not delete ten spaces from the calendar. It lands as `status="error"` with the exception in the record.
- **`--horizon-days 1` is a fast way to prove the clip works** without a fixture: `raw_count` stays at the VEVENT total while `horizon_count` goes to zero, and the source is still `ok`.
