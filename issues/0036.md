# 0036 — Poll the SpaceAPI directory for new Bay Area registrations

| | |
|---|---|
| **Status** | open |
| **Module** | research |
| **Platform** | All |
| **First seen** | 2026-08-05 |

## Description

Cheap recurring discovery. A space that registers with SpaceAPI is a space that wants to be aggregated, which makes the directory a higher-signal lead source than a generic search.

## Expected behavior

Periodically fetch `https://directory.spaceapi.io/` (249 spaces as of 2026-08-05, JSON name → endpoint URL), filter for Bay Area entries, and record any new ones. Update each space's `spaceapi:` block in `sources.yaml` with `url` / `status` / `checked`.

## Notes

**Current state:** exactly one Bay Area space is registered — Sudo Room — and its endpoint is **dead** (`api.sudoroom.org/status.json` 302s to a WordPress 404). Noisebridge is not registered at all. So there is nothing to harvest today; this is a lead source and an outreach lever, not a data source.

**Do not build a `spaceapi` adapter until at least one live local endpoint exists.** When one does, it is a thin wrapper: read `feeds.calendar.url` and hand it to the existing `ics` / `gcal_ics` adapter matching `feeds.calendar.type`. An adapter with zero sources would drift before it was ever used.

**Trap:** the top-level `events` field is **not** calendar events — it is recent occurrences in the space (door opened, member checkin). The calendar lives at `feeds.calendar`.

Treat any directory entry as a lead requiring verification, never a verified source. Sudo Room is the proof.

Related: issue 0034 asks spaces to publish endpoints; this issue notices when they do.
