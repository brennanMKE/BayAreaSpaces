## Description

Parse Bookwhen's server-rendered public agenda table. **Deterministic — no browser, no model.** Reusable for any Bookwhen-hosted space.

## Expected behavior

- Rows are `<tr data-hook="agenda_list_item">`.
- `data-event="ev-{entryid}-{YYYYMMDDHHMMSS}"` carries the exact local start time; title is the row's `<button>` text.
- Times are `America/Los_Angeles`.
- Default page returns 20 rows; paginate via `/{account}/calendar_items` **only if** the default window falls short of the horizon. Note that endpoint returns escaped HTML inside JS, not JSON.

## Notes

Verified 2026-08-05 on Sequoia Fabrica: 20 real events, 2026-08-13 → 2027-01-05.

This is a fallback. Once issue 0002 delivers the Bookwhen ICS token, that feed is better and this source should be demoted or dropped. It is worth building anyway — roughly 20 lines of deterministic parsing, and it unblocks Sequoia Fabrica's public class calendar today without waiting on a token.

Chosen over `llm_html` deliberately: the markup is regular enough that a small parser is both cheaper and safer than a model, and it generalizes to other Bookwhen spaces.

**Dead end already ruled out:** `events.sequoiafabrica.org` looks like a real events site, but every path (`/events.ics`, `/feed`, `/ical`) returns 200 as a redirect to Bookwhen.

## Root cause

Not a bug — a missing adapter. `sources.yaml` named `bookwhen_html` for Sequoia Fabrica's `bookwhen-agenda` source and `pipeline/cli.py` had it in the dispatch table with no parser, so the space's **primary public calendar** skipped every night with "adapter not yet implemented, see issue 0024". The only other source that space had running was the Google Calendar, which by its own `X-WR-CALDESC` carries *member and volunteer events only* — so the classes and socials, which are the whole public programme, were absent from the merged calendar.

The reason it needed a new adapter rather than an existing one: the space has no other machine-readable surface. `sequoiafabrica.org` is a static Next.js export with a 171-byte `__NEXT_DATA__` stub and zero JSON-LD; the wiki has no calendar; the Bookwhen public page carries no JSON-LD and exposes no feed link, so the real ICS feed's token is only obtainable from the Bookwhen admin (issue 0002).

## Fix

`pipeline/adapters/bookwhen_html.py`, wired into `ADAPTERS` in `pipeline/cli.py` with neither `paginates` nor `needs_source` — the `nextdata` shape: one request, no registry configuration, because the row hook and the `data-event` format are what make the adapter Bookwhen's.

- **Rows** are located by `data-hook="agenda_list_item"`. Bookwhen's own test hook is a better anchor than a CSS class: hooks exist so *their* tests can find these rows, so they move less often than presentation does.
- **`data-event="ev-{entryid}-{YYYYMMDDHHMMSS}"` is the whole reason this is deterministic.** `parse_data_event` decodes it with the 14-digit stamp anchored to the end (the entry id is opaque and may contain hyphens — one live event's does). The stamp is a server-written wall clock, so nothing reads `"Thu 13 Aug, 6:00 PM – 8:00 PM PDT"` out of a cell and guesses what year it meant.
- **Timezone** is attached in one place, as `America/Los_Angeles`, and `tz` carries a **resolvable IANA name** rather than an offset: `normalize.day_start_utc` and issue 0016's health filter both call `ZoneInfo` on it, and that filter runs *outside* the per-source try/except. `source_tz` records the offset that zone was actually at, written by the same `_offset_text` `jsonld` and `nextdata` use.
- **UID** is `{entryid}:{stamp}` → `{space_id}:{entryid}:{stamp}` after namespacing. The stamp rather than an epoch, so the UID cannot move if our timezone handling ever changes. `recurring=False`: Bookwhen gives each occurrence its own entry, so the occurrence start is already in the key.
- **Four named problems instead of an empty list.** `NOT_BOOKWHEN` (200 with somebody else's HTML), `NO_ROWS` (a Bookwhen page whose rows vanished), `NO_DATES` (rows present, no parseable `data-event`), and — not a problem — `reported_empty` when the agenda renders an explicit empty-state marker. One malformed row is skipped and *counted* (`bad_row_count`, `bad_row_values`); the other nineteen still publish.
- **`end` is always `None`.** The only end time on the page is inside a display string we have seen one variant of, and `DTSTART + a guess` renders a wrong block in every calendar client. `td.duration` is carried verbatim on `BookwhenEvent.time_text` for diagnostics. Same decision, same reason, as `embedded_json` refusing to turn `hours` into a `DTEND`.
- **Pagination is opt-in.** `fetch_bookwhen_html(paginate=True)` makes at most one extra request, and only when `looks_paginated` — a full 20 rows whose **last row** (pre-clip) still lands inside the horizon. `html_from_calendar_items` unpicks that endpoint's jQuery-wrapped escaped HTML via `json.loads` on each JS string literal. Sequoia Fabrica never trips it: its 20 rows reach 2027-01-05.
- Docstring records the fallback status, the `llm_html` comparison, and the `events.sequoiafabrica.org` dead end.

Also updated: `sources.yaml`'s adapter header comment, `pipeline/adapters/__init__.py`'s registered-adapter table, and the CLI docstring counts (eight of ten implemented; the other two are 0025 and 0028).

## Gotchas

- **`looks_paginated` must read the last *row*, not the last surviving event.** The first version read `events[-1]`, which is post-clip, so it answered "yes, fetch more" on every source including the one that already reaches 2027 — horizon clipping guarantees the last surviving event is inside the window. `BookwhenParse.last_row_start` exists for exactly this and is asserted in `test_a_page_that_runs_out_before_the_horizon_is_the_one_that_wants_more`.
- **The empty-state hooks in `EMPTY_HOOKS` were never observed live** — Sequoia Fabrica's page has had events on it every time anyone looked. That is recorded in the module, in the fixture and here rather than dressed up as verified. The direction of the guess is what makes it safe: an explicit marker is believed, and *absence* of one on a page with no rows is a reported `NO_ROWS` failure. Guessing the other way would silently delete a space.
- **The `data-event` regex must be greedy on the entry id.** One live event is `ev-sf-bioyarn-…` in the fixture's shape; a non-greedy or `[^-]+` id pattern reads the id as `sf` and the stamp as garbage. The 14 digits are anchored to the end for that reason.
- **`td.duration` is a trap.** It reads `6:00 PM – 8:00 PM PDT` and looks like a free `DTEND`. It is display text with one observed format, sometimes a bare duration; deriving an end from it would publish a wrong block that looks right. The ICS feed issue 0002 is chasing has a real `DTEND` — one more reason it supersedes this.
- **Reading the row's whole text content would "work" and be wrong.** The title has to come from the `<button>`; the row's `string()` is `"Thu 13 Aug 6:00 PM – 8:00 PM PDT Hand Embroidery Social Book"`.
- **`events.sequoiafabrica.org` will be found again.** It is referenced from the space's own wiki and every path on it 200s. There is a comment about it in the module docstring and a fixture (`not-bookwhen.html`) whose only job is to prove the adapter refuses that class of body.
- **Bare `<tr>` fragments parse fine.** `calendar_items` returns rows with no surrounding `<table>`; `extruct`'s lxml parser keeps them, which is why `agenda_rows` needs no wrapping. Checked rather than assumed.
- Implementing an adapter is a **cross-file** change: `tests/test_cli.py` carries `EXPECTED_RUNNABLE`, the implemented/pending adapter sets, the `validate` output assertions, *and* a per-adapter body in `calendar_transport()`. Without that last one the new source correctly reports `wrong_content_type` against the ICS fixture and the run's counts stop measuring the run.
