## Description

The highest-value adapter: `ics` alone covers Ace, Sudo Room, Noisebridge, Frontier (×2), Humanmade (×2), The Box Shop and Hacker Dojo. This is the reason the project is written in Python.

## Expected behavior

- Parse with `icalendar`, expand recurrences with `recurring-ical-events` over today → today+`horizon_days`.
- Handle `DTSTART;VALUE=DATE` (all-day), floating times with no `TZID`, and both bare-UTC `Z` and `TZID=` forms **within the same feed** — Sequoia Fabrica's calendar mixes them.
- Normalize Luma's multi-day-as-all-day behavior, which otherwise looks wrong when merged.
- Return post-expansion, horizon-clipped events. Raw VEVENT counts are close to meaningless here: Sequoia Fabrica has 89 VEVENTs and ~7 live; Maker Nexus 3645 and 171; Sudo Room 5057 pre-expanded to 2058 and 73 in horizon.
- Preserve the source UID for namespacing as `{space_id}:{source_uid}`.

## Notes

**Unbounded RRULEs are a real hazard, not a hypothetical.** Noisebridge's retired gCal has five RRULEs with no `UNTIL`; it generates ~5 plausible events a week forever. Expansion must be horizon-bounded, and issue 0016's `max_stale_days` gate is what catches the underlying rot.

Sudo Room's export ignores `scope`, `limit` and `category` entirely — byte-identical responses regardless — so all clipping is client-side.

Known-good fixtures to test against, with counts recorded 2026-08-05:

- Ace `calendar/list/?ical=1` — 126 VEVENTs
- Sudo Room `?ical=1` — 5057 VEVENTs, 73 in horizon
- Frontier `cal-Sl7q1nHTRXQzjP2` — 262 VEVENTs, 26 upcoming
- Hacker Dojo Meetup iCal — exactly 10, hard cap, no pagination

Save fixtures under `tests/fixtures/` rather than hitting the network in unit tests.

## Root cause

`pipeline/adapters/ics.py` did not exist — `pipeline/adapters/__init__.py` was a docstring listing the ten adapters and the issue that implements each. Nine of the registry's sources are `ics` and two more are `gcal_ics`, which is a wrapper over it, so until this landed the fetch layer from issue 0006 had nothing to hand its bytes to.

The design problem underneath is that an ICS feed's *shape* is not its *content*. Sudo Room ships 5057 VEVENTs and means 73; Noisebridge's retired gCal ships 28 and means zero, but generates ~5 a week forever. Any adapter that returns "the events in the file" gets both of those wrong in opposite directions, so the horizon window has to be a parameter of parsing rather than a filter applied afterwards.

## Fix

`pipeline/adapters/ics.py` exposes `parse_ics(FetchResult, *, horizon_days=120, today=None, now=None, strict_content_type=True) -> IcsParse`, with `parse` as the alias `sources.yaml`'s `adapter: ics` names and `parse_ics_text(text, ...) -> IcsParse` as the HTTP-free half that issue 0008 and anyone diffing two files out of `raw/` can call directly.

- **Expansion is bounded by construction.** `recurring_ical_events.of(calendar, skip_bad_series=True).between(today, today + horizon_days)` is the only path to an event. There is no unbounded materialization anywhere that a later filter trims, so five UNTIL-less RRULEs cannot explode: the Noisebridge fixture yields exactly 60 events over 120 days, 15 over 30 and 181 over 365, and moving `today` to 2031 changes the count, not the shape. Catching the rot itself is `max_stale_days` (issue 0016), and the data for it is here.
- **Counts are reported as two different numbers.** `vevent_count` is what the file holds; `event_count` is post-expansion inside the horizon. The Sudo Room fixture goes 6 → 3 and the Noisebridge one goes 7 → 60, in opposite directions, which is exactly why a single number cannot serve. `recurring_vevent_count` is carried too, since "0 RRULEs and 5057 VEVENTs" is itself a diagnosis.
- **All four DTSTART forms, and two of them in one file.** `dtstart_form` is `date` / `utc` / `tzid` / `floating` and `source_tz` is the TZID value, `"UTC"` for the bare-`Z` form, or `None`. Both are read from the **unexpanded** VEVENT, because `recurring-ical-events` applies `X-WR-TIMEZONE` and hands back a bare-UTC event already converted to the calendar's zone — see Gotchas.
- **Luma's multi-day-as-all-day is normalized.** RFC 5545 makes `DTEND;VALUE=DATE` exclusive, so a one-day event ends "tomorrow" and Luma's three-day hackathon ends on the fourth. `IcsEvent.end` is the **inclusive** last day, with `days` and `multi_day` alongside and `dtend_exclusive` if the original is wanted. The times Luma dropped are not recoverable and are not invented; the span is made honest and labelled so `emit` can render one banner rather than phantom instances.
- **The source UID passes through verbatim.** No namespacing, no synthesis, no fallback hashing — that is issue 0009's, and a test asserts the adapter does not do it. Because one UID covers 17 expanded occurrences, `instance_key` (`uid#start`) is offered as the material 0009 needs to tell them apart.
- **Staleness is scanned across the whole file.** `last_modified` / `dtstamp` are the newest values anywhere in the payload, **including VEVENTs outside the horizon**, and `last_change` / `stale_days` sit on top. Scanning only the expanded window would report Noisebridge as fresh, since its output is dated next week while every VEVENT in it is dated 2024. `stale_days` is `None` rather than `0` when a feed dates nothing, because "undated" is not "fresh".
- **"HTTP 200 is not success", reported rather than raised.** The content type goes through `FetchResult.expect_content_type(*CALENDAR_CONTENT_TYPES, allow_missing=True)` with `content_type_is()` for the lenient path, and the body is sniffed for `BEGIN:VCALENDAR` regardless — a `text/calendar` header over a copy of the homepage still fails. A bad payload never raises and never returns a silent empty list: it returns `ok=False` with an `IcsProblem` (`TRANSPORT`, `NOT_MODIFIED`, `EMPTY_BODY`, `WRONG_CONTENT_TYPE`, `NOT_CALENDAR`, `UNPARSEABLE`) and a message naming what was expected and what arrived. `text/plain` over a real VCALENDAR is tolerated and says so in `error`; `text/html` never is.
- **`IcsParse` is list-like where that helps and not where it hurts.** `__iter__`, `__len__` and `__getitem__` delegate to `events`, but `__bool__` is the *verdict*: an empty-but-valid feed is truthy (The Box Shop runs 8–12 events a year and is routinely zero — that is `allow_zero`'s problem) while a `text/html` body is falsy. Both hold zero events, and confusing them is the failure this project keeps trying to eliminate.
- **Feed metadata for issue 0008.** `prodid`, `calendar_name` (`X-WR-CALNAME`), `calendar_description` (`X-WR-CALDESC`), `calendar_timezone` (`X-WR-TIMEZONE`) and `refresh_interval` (`REFRESH-INTERVAL` or `X-PUBLISHED-TTL`).

## Gotchas

- **`recurring-ical-events` applies `X-WR-TIMEZONE` and rewrites bare-UTC starts.** A `DTSTART:20260813T020000Z` on a calendar declaring `X-WR-TIMEZONE:America/Los_Angeles` comes back as `2026-08-12 19:00-07:00`. The instant is preserved, so nothing is *wrong* — but reading the zone off the expanded value would report every Sequoia Fabrica event as `TZID=America/Los_Angeles` and erase the evidence that the feed mixes forms. `dtstart_form` and `source_tz` are therefore read from the unexpanded VEVENT, matched back by UID.
- **A floating time on a calendar with no `X-WR-TIMEZONE` stays naive**, and this adapter passes it through naive on purpose. Issue 0009 is the chokepoint where a naive datetime becomes a hard failure; silently guessing a zone here would defeat that assertion before it ever ran.
- **`between(today, today + 120d)` covers days 0–119.** The stop bound is midnight on day 120, so an event at 19:00 on the 120th day is out. That is the intended reading of "today → today + `horizon_days`", but it is off by one from "121 dates inclusive" and `test_the_horizon_boundary_includes_the_last_day_and_excludes_the_next` pins it.
- **`UID` is not unique after expansion.** One RRULE yields 17 occurrences sharing a single UID, so `{space_id}:{source_uid}` applied naively would collapse a whole series into one event. `instance_key` exists for this; issue 0009 has to decide the rule.
- **`RECURRENCE-ID` is set on *every* occurrence**, including non-recurring ones, so its presence cannot be used to detect a series. `IcsEvent.recurring` is derived from `RRULE`/`RDATE` on the source VEVENT instead.
- **`str()` does not round-trip typed properties.** `REFRESH-INTERVAL` parses to a `timedelta` whose `str()` is `"12:00:00"`, not `"PT12H"`, and `ORGANIZER` stringifies to the bare `mailto:` while the human name lives in the `CN` parameter — which is the useful half for Frontier Tower, where the addresses are anonymous Luma relays. Both are handled explicitly.
- **All-day events carry `datetime.date`, not `datetime.datetime`.** `start` and `end` change type with `all_day`, and mixed `date`/`datetime` values cannot be compared, which is why sorting goes through an explicit key. Anything downstream that assumes `.tzinfo` exists will break on The Box Shop.
- **A 304 is `ok=False`.** It is `IcsProblem.NOT_MODIFIED` rather than a transport failure precisely so issue 0014 can reuse the stored events instead of publishing zero — but a caller that only checks `ok` will read it as a failed source. Branch on `problem`.
- **`vevent_count` is not a health signal and should not be alerted on.** It is in the run report so a human can see 5057 → 73 and recognize it as normal for Sudo Room. `event_count` is the number the gates take.
